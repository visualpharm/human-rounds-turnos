## 2026-10-30 · Launch signals (TASK-4): closed failure codes, a daily digest of numbers and Sentry Crons, all behind `TURNOS_SENTRY_SIGNALS`
Decided: an installation whose logs and database the developers cannot read (salud.pinamar.gob.ar behind the municipal gateway) tells its OWN Sentry project three things, each one switch of the comma list `TURNOS_SENTRY_SIGNALS` (`failures`, `digest`, `crons`, or `all`; unset = nothing, and nothing happens without `TURNOS_SENTRY_DSN` either). (1) `failures`: every place that swallows an error on purpose reports a CLOSED code through `launch_signals.handled(code)` (ten codes: `mail_failed`, `whatsapp_failed`, `reminders_sweep_failed`, `waitlist_sweep_failed`, `hsi_sync_reschedule_failed`, `backup_data_upload_failed`, `backup_data_journal_failed`, `backup_data_reschedule_failed`, `backup_full_failed`, `digest_failed`) — the event message IS the code, the tag `failure_code` carries it, no argument and no text exist, at most one event per code per 15 minutes per process; a code outside the list is dropped. (2) `digest`: staff sign-ins (ok / failed), mail and WhatsApp (sent / failed) and every code above are added to an hourly counter (`launch_signal_counters`, Alembic 0036: an hour, a code from the list, a number); once a day after 12:00 UTC the worker (or, without a worker, a web thread) sends ONE info event whose `contexts.launch_digest` holds integers under 30 closed keys: requests created / approved / rejected / cancelled in 24 h and pending now (no reasons), the HSI outbox by state and open conflicts, the worker queue (waiting, running, age in seconds of the oldest due job, failed in 24 h), the age of the last stored data file and of the last verified full backup, the schema revision, the number of sections that could not be read (`sections_failed`: a missing measurement is told, not silent; a backup age of -1 means there is no such backup yet) and the counters of the last 24 whole hours (24 to 25 hours of counts). The day is claimed by a row in the counter table, so two processes send one digest; a digest that crashes or that the client refuses gives the claim back and reports `digest_failed`, one that was handed to the client stays sent whatever happens to the housekeeping after it, and a process killed between the claim and the send loses that day's digest (a window of milliseconds). (3) `crons`: Sentry Crons check-ins — `turnos-worker` (every 5 minutes, from the maintenance queue), `turnos-reminders`, `turnos-waitlist`, `turnos-backup-data` and `turnos-backup-full` (a check-in only when a full backup actually begins: `in_progress` at its start, so even a first run that hangs is a runtime alert, then ok or error) — started then ok or error; a silent worker or backup is a missed check-in in the project's monitors. What leaves is rebuilt from an allowlist in `error_tracking.scrub_event` (a listed `failure_code` tag, `launch_digest` integers under listed keys, a check-in of a plain slug + one of three statuses + whole numbers + UTC + a crontab of digits or an interval in minutes; a launch-signal event carries no breadcrumbs); `test/test_launch_signals.py` proves it with the real SDK and real patient and staff rows (no DNI, name, phone, address or message in the envelope), a real `worker.py` process against a local stand-in for Sentry was run once end to end, and each mutation of the signal code turns the test red. Default installations change nothing: no new required setting, one empty table, no extra job in the worker (the heartbeat task is registered only while a signal is on), and with a signal on the worker's client runs in `signals_only` mode (no default or auto-enabled integration: it reports no error or log of its own, only the signals; the web process keeps its existing error reporting); a counter write waits at most 500 ms for the hourly row and then gives the count up.
Why: hospital's TASK-4 (runbook K-2…K-4): salud has been live since 2026-10-30 17:44Z and we can see neither its logs nor its database; a mail provider that stops delivering, a worker that dies or a backup that goes quiet would be found by a patient first · Rejected: a message text or the rejection reason in the events (free text can carry a person); full error reporting in the worker as a side effect of a signal switch (a separate decision if wanted); counting by patient or by staff name; a separate Sentry project or a second transport; sending the digest from the web process on every installation (two processes would send two); enabling any of it by default · Undo: unset `TURNOS_SENTRY_SIGNALS` — the code is inert again; the counter table is forward-only and holds numbers a day old at most · By: agent (hospital)
Source: `core/launch_signals.py`, `ops/launch_digest.py`, `core/error_tracking.py`, `alembic/versions/0036_launch_signal_counters.py`, `worker.py`, `core/queue_infra.py`, `ops/backup_full_queue.py`, `ops/data_backups_queue.py`, `test/test_launch_signals.py`.
