## 2026-10-26 · A live waitlist offer holds its time: the wizard does not list it and nobody else can take it
Decided: the email of a waitlist offer says «por 5 minutos este turno es tuyo, garantizado», but until now the public wizard kept listing the time and a stranger could ask for it. An offer that is still claimable (`appointment_offers.status = 'ofrecida'` and `expires_at` in the future) now counts as taken for the wizard's list of taken times (`slot_holds.taken()`, which the band and the wizard grid read) and for `slot_holds.try_take` (the slot-hold endpoint, the final submit, the patient's reschedule and the desk's «Crear turno»). ## 2026-10-26 · The municipal installation (`*.gob.ar`) never deletes or overwrites a backup, by any path: one lock in both remote clients, the upper paths skip or refuse first
Decided: (1) One lock, `core.backup_lock` (only `core.config` behind it; `locked()` = `core.config.government_installation()`, the marker of the previous entry), asked by the two remote clients before a byte leaves. The B2 native API of the data/ backups goes through `ops.data_backups._req_json`, which calls `check_b2_call`: on a government installation only the calls in `B2_ALLOWED` leave (`b2_authorize_account`, `b2_get_upload_url`, `b2_upload_file`, `b2_list_file_versions`, `b2_list_file_names`, `b2_get_file_info`, `b2_download_file_by_id`) — `b2_delete_file_version`, `b2_hide_file`, `b2_copy_file`, `b2_cancel_large_file`, bucket changes and anything unknown are refused (an allowlist, not a list of the dangerous ones). The S3 transport of the encrypted full backups (`core.backup_s3.S3.request`) calls `check_s3_request`: no DELETE of any kind — on B2 an S3 DELETE by name is a hide marker and needs only `writeFiles`, so a key without `deleteFiles` does not stop it; the lock does —, no multi-object delete, no server-side copy, and a new object (a PUT that is not a part, or the start of a multipart upload) only when a HEAD answers 404, checked again before every retry (a PUT whose answer got lost finds its name taken and stops); any other answer is not «free» — a 401/403 says the key must be allowed to read and list objects (AWS answers 403 for a missing object without `ListBucket`; B2 and R2 answer 404). A refusal raises `BackupWriteForbidden` («sin permiso en esta instalación») and logs one `ERROR` line without names, values or keys. (2) Overwrite. The full backups are named `hr-full-<uuid>.hrb`, new every run, and the HEAD makes it a check, not a hope. The data/ backups used the path as the name (`data/cuenta-fotos/<dni>.jpg`), so a changed file went to the same name: in B2 a new version, and with a lifecycle that keeps only the last version, the old copy gone. On a government installation every upload is content-addressed: `<prefix><path>~<sha256 of the bytes>` (`backup_lock.addressed_name`), and the client checks the suffix against the bytes it sends — one name can never hold two contents, a changed file goes to a new name and the old one stays; content that comes back (A → B → A) is not sent again — the sweep reads the receipt ledger once (`backup_version_rows`, on the sweep's own connection) and points the journal back at the stored receipt of that name; without the ledger nothing is uploaded that pass. Names already uploaded before this change keep their plain form and are not re-sent while the file is unchanged (`ops.data_backups._row_names_path` accepts both forms); `restore_version` puts a content-addressed version back on its plain path (the suffix is removed only when it is that version's own SHA-256). The test stands keep the plain names; a purge there also finds and deletes the `~<sha256>` copies of a path (an installation that stopped being recognised as municipal must not mark a path purged while its copies stay). (3) The upper paths check first, so nothing is left half done: the remote purge (`_purge_remote`) returns before listing (a real sweep there had no delete primitives already, step 1); the operator's exact delete (`data_backups_restore.delete_remote_version`) and an applied data/ retention (`apply_retention(dry_run=False)`) are refused before the first request or candidate — listing, reconciliation, the dry-run plan and restores stay; the rotation of the full backups (`backup_full.apply_retention`) returns before downloading anything when `TURNOS_BACKUP_RETENTION_APPLY=1`, the backup itself still succeeds; a failed multipart upload is not aborted and `cleanup_incomplete` sends nothing (both are DELETEs; the bucket's lifecycle can cancel unfinished uploads); the connection probe («Probar conexión» in Settings and in the setup) writes, reads back and keeps its 32-byte `connection-test-<uuid>` object, and Settings say so («El objeto de prueba queda en el bucket…», `backup.probe_ok_kept`). (4) The manual tools and the loud signal, as in step 1: saving the rotation switched on from Settings (`api_keys` group) or the setup is refused with `backup.forbidden` («Sin permiso en esta instalación: la aplicación no borra ni sobrescribe copias de seguridad…»); the screens are unchanged (the switch and the buttons stay, the server answers). A rotation switched on by the environment or an older panel value does not stop anything: an `ERROR` line at the start of the web process and of the worker's full-backup job (`purge_guard.warn_rotation_ignored`) and in every full backup, and a `warn` «Rotación de copias · Ignorada en esta instalación» in the «Copias de seguridad» block of «Sistema» (`backup.rotation_ignored.*`). Five new keys of `backup.json` in the ten languages (es/en by hand, the eight generated ones written by hand with their `_source_hash` entries). (5) `test/test_backup_lock.py` holds it: an inventory over the code (AST) of every B2 native call name, every network send of a module that speaks B2 or S3 (`b2api`, `AWS4-HMAC`, `x-amz-`), the order lock-before-send in both clients, and every call or hand-over of a method that deletes or writes remotely — a new one fails until it is listed with what holds it on `*.gob.ar`; no storage SDK (boto3, botocore, b2sdk, minio, s3fs…) is imported and no storage CLI (`b2 rm…`, `rclone`, `aws s3`, `s3cmd`) appears in code, shell or deploy files; a file the scan cannot parse fails it; then every path on a government origin and on a test stand. The inventory counts calls (a second call in an already listed place fails it too). A real `backup_full.run` through the real S3 client on an in-process endpoint: six backups on a government origin upload and verify with a HEAD before every PUT and no DELETE although the rotation had candidates; the same on a test stand rotates. Nineteen mutations removing a check (each client check, the check before a retry, each early return, the settings and setup refusals, the HEAD and its 403 text, the DELETE rule, the purge of addressed copies, the reuse of a stored receipt) each turn it red. · Why: Product owner, Teams 2026-10-26 19:48 UTC (TASK-45, after 0983d03d), the municipality's words: «cerralo para todo: la purga remota, la rotación de respaldos completos y las herramientas manuales de la app. La app puede escribir respaldos;
