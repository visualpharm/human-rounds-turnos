## 2026-10-25 · A lab result the patient deletes is gone; files the retention deleted stay deleted in B2
Decided: (1) The patient's «delete» of an uploaded lab result sets the file, its transcription and
its filename to NULL (the emptied row stays as the record) and deletes the cached AI reading of that
report. (2) The uploaded lab FILE (bytea) expires after `TURNOS_LAB_UPLOAD_RETENTION_DAYS`, else the
referral files' `TURNOS_REFERRAL_RETENTION_DAYS` (default 180): the bytes go NULL, the transcription
stays; any value <=0 keeps everything, so the municipal installation's `TURNOS_REFERRAL_RETENTION_DAYS=0`
still means «do not clean». (3) The referral-file retention writes the path in the new `purged_files`
journal BEFORE deleting; the B2 sweep then deletes every remote version of journaled paths (exact file
ids, tombstoned, retried), never uploads them again, `restore_version` refuses them, and the next
retention pass removes one that came back. Expired `ordenes/pending/*` uploads lose their B2 copies
too. `TURNOS_BACKUP_PURGE_REMOTE=0` turns the B2 deletion off. A file that merely vanishes from the
volume never triggers a remote deletion.
Why: hospital schema review №11 — «delete» only set `deleted=now()` and the file stayed in the table
and in every dump; lab files had no retention; B2 kept every referral file the retention had removed
from the server, and a restore would bring them back.
Agent calls (reversible): the lab window follows the referral window (no new policy number); the
file expires but the transcription stays (it is what the doctor reads); additive Alembic
`0029_purged_files` (one new table, no backfill, chained after `0028_data_subject_requests`); the
file step of the Ley 25.326 erasure (`core/subject_erase._remove_files`) records every REFERRAL file
it removes in the same journal, so those files lose their B2 copies and are not restored either
(a profile photo is not journaled: its path `cuenta-fotos/<dni>.<ext>` would keep the DNI the
erasure removes, so its B2 copies stay a manual cleanup); the encrypted `backup_full` archives
are not rewritten (they age out under their own `RETAIN_*` schedule).
Undo: revert the commit; the table is harmless to leave. Re-uploading deleted B2 copies is not possible.
By: agent (technical choice inside the agreed slice); the 180-day window and the default-on remote
deletion are flagged under «Needs your decision» in the MR.

`modules/turnos/booking_requests.py` (`sweep_referrals`, `reapply_purged_files`),

## 2026-10-25 · Dates and times are `date` / `time` in the database
Decided: `slot_holds.day` / `slot_holds.time`, `lab_report_analysis.fecha` and `patient_lab_uploads.fecha`
are `date` / `time` / `date` (Alembic `0030_date_time_columns`; `_SCHEMA_SQL` declares the same for fresh
installs). «9:00» and «09:00» are one slot to the `UNIQUE (service_id, day, time)` guard, and
«2024-13-45» cannot be stored even by a writer that bypasses the code. The code and the API are

(`db.hold_acquire` answers False, `POST /api/slot-hold` answers 400); a report date that is not a
real ISO day is stored as «no date» instead of raising.
Why: problems.md №13 — text dates are a trap, not a fire (the code wrote valid values); closed while the
tables are tiny (production held 5 `lab_report_analysis` rows, 0 uploads, a few minutes of holds).
Agent calls (reversible): the revision never raises on data and never destroys it — an impossible `fecha`
becomes NULL, an ISO day with a time suffix keeps its day, a hold with an impossible day/time or a
repeat of the same slot leaves `slot_holds` (the one linked to a request wins, then the newest; a pending
request's chosen time lives only in its linked hold, so the loser matters), and every value or row that
could not be kept is first copied whole into `date_time_conversion_leftovers` (a normal, normally empty table: in `_SCHEMA_SQL`, created by the revision, registered as «no personal data»)
with the reason, and logged by id; `scripts/fixes/report_fechas_texto.py` lists those rows read-only
before upgrading. The bridge for
pre-Alembic partial installs treats the old `text` type of these four columns as «converted by the
upgrade that follows» (`migrations.FORWARD_REVISION_COLUMN_TYPES`) instead of a gap its USING-less

report date falls back to the upload day instead of being dropped.
Undo: `alembic downgrade 0029_purged_files` turns the columns back into text (rows set aside
or NULLed by the upgrade stay so; their originals are in `date_time_conversion_leftovers`); do not
revert the commit while the database is stamped 0030.

## 2026-10-25 · A schema change is an Alembic revision and nothing else; the first revision is a frozen file

schema change in review) and `TestSchemaSnapshot` compares with a real fresh boot. The access-log
guard SQL moved from `db.py` into revision 0026, which is the only place that applies it. ·
Why: the double write («`_SCHEMA_SQL` plus a revision», added 2026-08-08 in the review rounds that
followed the cutover) was a consequence of the baseline importing the live string, not a product
rule: the Tier 4 design (`docs/roadmap/tier4-replatform-design.md`, «Alembic (slice 4)») already said

Pinamar launch workstream, asked for it on 2026-10-25 (it also unblocks foreign keys, which the shape

old string) · By: agent (design, implemented under the owner's request of 2026-10-25).

## 2026-10-25 · Foreign keys: the database refuses to delete a parent that still has children
Decided: Alembic `0032_foreign_keys` adds 18 foreign keys for the links whose parent is a real row
(`core.db.FOREIGN_KEYS`; the revision keeps its own frozen copy): attendance/appointment history, holds, waiting
list and interviews → `booking_requests`; offers → `waitlist`; consultations and the health profile's source →

## 2026-10-25 · Recovery links are stored as a hash, and a password change voids the account's other links
Decided: `reset_tokens.token` holds `sha256(token)` (hex), never the token that travels in the emailed link;
the link is unchanged and is looked up by its hash, the same way `admin_reset_tokens` works. `db.set_password`
(link reset, OTP reset, any other path) marks every still-unused recovery link of that DNI as used, so an older
link from a previous email cannot change a password that was already recovered. Alembic
`0033_reset_token_hash` converts the rows written before: used or expired rows are deleted, the still-open ones
are hashed in place (a link emailed just before the upgrade keeps working; no raw token is left in the table).
The schema does not change (same column), so `alembic/schema-head.txt` only moves its head name ·
Why: finding of the sqla-5 executor, 2026-10-25: anyone able to read the database could build a working
recovery link, while OTP codes were already hashed; the owner (2026-10-25) has the agent side do everything that
is not interface work · Rejected: renaming the column to `token_hash` (the cosmetic gain does not justify
touching the boot classification of three database shapes); deleting every open link in the migration (it would
break links patients had just received for no security gain, since the hash leaves nothing reversible);
invalidating older links when a NEW one is requested (changes what a patient who asks twice experiences, not
asked for) · Undo: `git revert` of the code commit is enough for the app, but rows already hashed make any link
emailed before the revert unusable (they expire in an hour; the patient asks for a new one); the revision is
forward-only · By: agent (technical choice inside the agreed slice).

## 2026-10-25 · Chat retention: a configurable period, OFF until the hospital sets it
Decided: the housekeeping sweep can delete chat rows by age. `TURNOS_CHAT_RETENTION_DAYS` (days, minimum
30; unset or 0 = off) deletes the messages of every chat channel — web with a login, web without one,
WhatsApp — older than the period, summarised or not (`db.purge_chat_by_age`); then
`TURNOS_CHAT_SUMMARY_RETENTION_DAYS` (default: the same period) deletes `chat_summaries` and
`chat_compactions` whose last covered message is older (`db.purge_chat_summaries_by_age`). Messages
always go first. The `interview` channel (the pre-consultation transcript) is clinical record and is
never touched. The default stays OFF — the hospital decides the period — so nothing changes in any
installation until someone sets the variable. `scripts/fixes/report_chat_retention.py` previews, read-only
and counts only (its connection is opened read-only and never goes through `db._connect()`, so it cannot
migrate the schema), what each candidate period would delete. The old rule (summarised messages over 90
days) is unchanged except that it too now skips the `interview` channel.
Why: problems.md №12 — summaries were never deleted and WhatsApp / no-login messages could not be
deleted at all: symptoms and complaints in the patient's own words, kept forever without a period.
Agent calls (reversible): a value under 30 days or not a number is treated as OFF with a log line (a
typo must not wipe last week's conversations); `TURNOS_CHAT_SUMMARY_RETENTION_DAYS`, when set, always
wins — `0`, a typo or a value under 30 means «summaries are not deleted by date», it never inherits the
messages' period; the sweep deletes messages in batches of 2000, up to 20 batches per pass, and summaries
and compactions up to 2000 of each per batch, so a large backlog may take more than one pass; summaries
age by `covers_until` (the last message they cover), not by when they were written — a compaction of a
chat that is still going keeps advancing, so the period counts inactivity, not the age of each fact;
`chat_handoffs` (web-to-WhatsApp codes, which hold the phone that redeemed them) are not part of this
and still never expire from the table.
Undo: unset the variables (rows already deleted stay deleted); revert the commit; no schema change.
By: agent (the mechanism); the period itself is the hospital's — see the merge request.
Source: `core/db.py` (`purge_chat_by_age`, `purge_chat_summaries_by_age`, `chat_retention_preview`),
`ops/housekeeping.py` (`purge_chat_by_retention`), `scripts/fixes/report_chat_retention.py`;

## 2026-10-25 · SQLAlchemy Core: the schema is described as code, new queries are Core statements, the move is staged
Decided: (1) `core/schema_model.py` describes every table of a fresh install in SQLAlchemy Core
(`MetaData`/`Table`, no ORM classes); a database built from it alone must equal
`alembic/schema-head.txt` (`test/test_schema_model.py`), so a schema change is the model edit PLUS a
forward Alembic revision in one commit. (2) `alembic/env.py` points `target_metadata` at the model:
`alembic revision --autogenerate` proposes the revision and `alembic check` reports drift, but the
revision's SQL is still written and read by hand (triggers, functions and backfills are never
autogenerated). (3) New query code uses SQLAlchemy Core statements run through `core/sqlcore.py` on the
psycopg cursor of `db._connect()` — the same pool, the same transaction, the same dict rows; no
`Engine`, `Session` or ORM for the application. (4) The ~600 hand-written statements move module by
module in later stages, each behind a test that pins the module's behavior before the rewrite; stage 1
converts `modules/turnos/waitlist_store.py` as the sample. ·
Why: the schema now has one source (Alembic) but was only readable as SQL text; the model makes it
checkable in code (names, types, constraints) and lets a query be built from the same names instead
of repeated strings, and the staged move lets each module be proven one to one before the next
(maintainer, who runs the Pinamar launch workstream, decided on 2026-10-25 to move to SQLAlchemy in stages, not all at once) ·
Rejected: the ORM (mapped classes, sessions and identity maps would change every function's
semantics at once; the code base passes dict rows and plain values); an SQLAlchemy `Engine` over the
pool (a second owner of connections and transactions, `reset on return` would roll back the
caller's work); bind casts on every parameter (the dialect's default — they change what the database
receives for values the hand-written SQL sent bare); regenerating the model from the database in a
test (the snapshot test already is that check, in the other direction) · Undo: revert the commits —
the model, `sqlcore` and the converted module are additive, no revision or table changed ·
By: agent (design, implemented under the owner's decision of 2026-10-25).

Decided: (1) `study_store`, `core/backup_journal.py`, `ops/demo_refresh_store.py`, `config.guardar`,
