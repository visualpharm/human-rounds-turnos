## 2026-10-24 · The HSI extension serves salud.pinamar.gob.ar through an optional permission, not a manifest host
Decided: extension 0.4.0 adds salud.pinamar.gob.ar without touching `host_permissions`
or `content_scripts`. The site is listed in `TURNOS_OPCIONALES` (`lib/shared.js`) and
rides on the existing `optional_host_permissions: ["https://*/*"]`; once Chrome allows
`https://salud.pinamar.gob.ar/*`, the service worker registers the row script for its
`/admin/*` (`chrome.scripting.registerContentScripts`, persistent) and injects it into
an already open tab; a removed permission unregisters it (`permissions.onAdded/
onRemoved`). The operator allows it with one click — the popup's «Activar en
salud.pinamar.gob.ar» — or on «Guardar» in the settings, where «¿Dónde ves los
turnos?» starts ticked (one Chrome prompt for HSI and the site). The server's «Turno
creado» offer (`_hsi_extension_url`) reads both lists, so the extension stays the one
list of sites it serves.
What the desk sees on the update: nothing changes on pinamar.humanrounds.org and the
demo; no permission prompt and no disabled extension. On salud the row buttons appear
after the one «Activar» click and Chrome's «Permitir».
Why: a new required host (in `host_permissions` or a static content script's
`matches`) is a permission increase; Chrome disables the updated extension for everyone
who has it until they accept again
(developer.chrome.com/docs/extensions/develop/concepts/permission-warnings) — the whole
desk would lose the button on the morning of the update. Found by the maintainer's agent on MR 62.
Rejected: salud in `content_scripts` (the disable above); opening the settings tab on
update (interrupts the desk mid-work); `permissions.addHostAccessRequest` (needs a tab
the worker cannot see without the permission). Undo: revert; 0.4.0 → a later version
without the entry. By: agent.

## 2026-10-24 · One SIGTERM during the worker's signal handoff is one signal
Decided: `_boot_and_run` hands SIGTERM/SIGINT from `main()`'s plain handler to
asyncio through `_install_async_signal_handlers` (`worker.py`): both
`loop.add_signal_handler()` calls run with the two signals blocked on the main
thread (the mirror of `_restore_main_signal_handlers`), and a plain-handler
call that happens inside that handoff is recorded as an echo, so the asyncio
callback for the same signal within `_HANDOFF_ECHO_TTL_S` (1 s) is absorbed
instead of counted. Second-signal behaviour is otherwise unchanged: a genuine
second SIGTERM/SIGINT still exits with `EXIT_FORCE_KILL` (3). · Why:
`add_signal_handler()` arms `signal.set_wakeup_fd()` before it replaces the
plain handler; one signal in between reached both channels, the shared
counter read two, and the worker took the force exit (3) instead of a graceful
stop (0) — the 1-in-40 failure of
`test_rapid_spawn_sigterm_never_orphans_worker_row`. The mask alone is not
enough: the kernel hands a process-directed signal to any thread that does not
block it, and the worker already has its health and DB-pool threads at that
point (`TestAsyncSignalHandoff`'s other-thread case stays red with the mask
only). · Rejected: the mask alone (above); blocking the signals in every
non-main thread (the pool threads belong to psycopg_pool and are created
elsewhere); replacing asyncio's signal handling with our own wakeup socket
(rewrites a reviewed contract for a microsecond window). Cost, deliberate: a
second signal within 1 s of one that landed in the microsecond window counts
once, as Python itself coalesces signals it has not yet dispatched. · Undo:
revert the commit. · By: agent.
Source: `worker.py` (`_install_async_signal_handlers`, `_SignalState`),
`test/test_queue_worker.py` (`TestAsyncSignalHandoff`).
