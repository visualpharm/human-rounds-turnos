## 2026-10-21 · Server logs never carry an exception's message
Decided: every log line of the server code writes a caught exception as its
type and code (`log_pii.exc`: HTTP status, errno or Postgres SQLSTATE), never
its text; a traceback keeps frames and exception types, never values
(`log_pii.traceback_text`/`print_traceback`); conversation keys (`tel:…`,
`dni:…`) are masked (`log_pii.key`), and an email subject is never logged (the
masked recipient instead). `log_pii.install()` in `asgi_main.py` and
`worker.py` extends the same rule to what libraries log (uvicorn's «Exception
in ASGI application», procrastinate, asyncio) through the LogRecord factory,
and to uncaught exceptions in any thread. Privacy section 6 now says so
instead of admitting that a failure line can echo a database message. Pinned
by `test/test_logs_pii.py`: an AST gate over the server code (no raw except
variable in a log call, no `traceback.*`, no `exc_info`) plus runs of the
usual failure paths with synthetic name/DNI/phone/email/key.
Why: Product owner, 2026-10-21 — everything about the logs before the launch; the
municipality's platform team reads them. · Rejected: sweeping the message
with `log_pii.text` (no regex catches a name); converting `scripts/` and
`vendor/` (developer tools on a developer machine, not server logs) and
`manage.py`'s own validation messages to the operator's terminal. · Undo:
revert the commit. · By: Product owner (ask), agent (shape).
Source: `core/log_pii.py`, `asgi_main.py`, `worker.py`, `patient_web/legal.py`,
`test/test_logs_pii.py`.

## 2026-10-23 · Clinical access log, own-patient rule, app role without schema rights (K10)
Decided:
- **Every staff read of clinical data leaves a row** in `clinical_access_log`
  (who, when, which screen, which patient, allowed or denied) — the ficha,
  interview, consultation, AI summary, HSI history, red alerts, referral file,
  and the lists that carry triage or the referral's AI reading (one row per
  patient shown, once per day per (who, what, patient, target) and process —
  the lists refresh all day). Denials are recorded too.
- The patient is an **HMAC of the DNI** (`TURNOS_ACCESS_LOG_KEY`, fallback
  `TURNOS_ADMIN_SECRET`), never the DNI: searchable by DNI, a dump lists no
  documents. A DNI correction does not rewrite it.
- **Append-only in the database**: a trigger refuses every UPDATE and every
  DELETE outside the age purge, never younger than one year. Retention is a
  setting, `TURNOS_HOUSEKEEPING_ACCESS_LOG_DAYS`, default ten years.
- **A read whose row can't be written does not happen** (503): no unrecorded read.
- **Own patient** = a request of that clinical DNI assigned to or booked in the
  doctor's agenda, or an interview addressed to the doctor; no date or status cut.
  On the doctor's screens (`atencion_medica`) only the admin sees anyone; every
  other role — including custom roles granted «atención médica», which used to
  see everything — is held to the doctor linked to its account. The desk's
  screens stay by role; a medico is held to their own there too (even with
  «pacientes» granted).
- The doctor's exact-DNI search still finds someone who is not theirs (identity
  only — the 2026-08-05 walk-in case), and the hit is logged as `busqueda`.
- «Quién abrió sus datos» in the ficha, admin only (permission `usuarios`).
- The app can run as a **role without DDL** (`scripts/db_app_role.py`, dry-run by
  default); the boot migrates through `TURNOS_DB_MIGRATION_URL` (schema owner,
  same database or the boot refuses). Unset = one login, as before.
Why: Ley 26.529 art. 18, Ley 25.326 arts. 9-10, Res. AAIP 47/2018; K10 of the
launch plan (stack review 2026-10-22: “the chart, the AI summary, labs,
interviews and referrals can be opened without a trace”; the AI summary
answered any DNI).
Rejected: plain sha256 of the DNI (10^8 DNIs brute-force in seconds); logging
only single opens and not the lists (the day queue shows interview summaries to
the desk); a TRUNCATE trigger (the test fixtures truncate every table; the app
role simply lacks TRUNCATE); closing the doctor's exact-DNI search (it is how a
walk-in gets a free slot).
Undo: revert the commits; the table is additive (0026) and can stay.
By: agent (owner's launch plan, sent to the product owner 2026-10-23; the product owner's hub (Teams 23.10) raised no objection —
not a request of his own). Refusals to someone else's patient answer 404, not
403, per the product owner's existing rule (admin-cola-y-agenda.md: if you can't see it, it
doesn't exist for you); the access row still records them as denied.
Source: docs/architecture/registro-de-accesos.md; core/access_log.py; tests named there.

## 2026-10-23 · A request's doctor is one pair: id is the truth, name comes from the catalog
Decided: `assigned_doctor_id` identifies the doctor; `assigned_doctor` is the
catalog's name for it. ONE write rule (`doctor_appointments.resolve_pair`) for
approval, `/assign`, the auto-suggestion and the HSI resolver: a known id →
catalog name; a bare name → id only if it resolves to exactly one catalog
doctor, else id NULL (never a previous doctor's id). `db.approve` writes the
pair whole instead of two per-column `COALESCE`s. Identity reads (busy minute,
suggested slots, desk overbooking, `count_appointments_of`, «Mis turnos» /
«Mis pacientes») go by id; the stored name only matches legacy rows without
one. Display reads prefer the catalog name by id (`display_name`).
Renaming: BOTH halves — `db.catalog_upsert('medicos')` rewrites the stored
name of the doctor's rows in the same transaction (so every reader of the
stored name — emails, HSI hints, reports, panel search — is right without
touching each one), and the main display surfaces read the catalog name by id
(covers a rename shipped in a pack, which never passes through the DB).

ids / fixes names; ambiguous ones are only reported). No migration — no schema
