## 2026-10-28 · «Cerrar sesión» ends the staff session for good: a copy of the cookie made before signing out stops working
Decided: the staff cookie `st_admin` stays a signed token with the same payload; its session id is its `nonce`, and a renewed or re-issued token carries that id forward as `sid` (a fresh cookie must not gain a second random field: the J28 journey reads its payload as plain base64 JSON, which itsdangerous only keeps when it does not compress it). Signing out (`POST /api/admin/logout`) lists the id in the new table `admin_session_revocations` (Alembic `0035`) and `admin_auth._verify_token` — the one place every gate, screen and `whoami` verify a cookie — refuses a listed id. The renewal `whoami` does and the cookie the account rename re-issues carry the SAME id, so a copy made before a renewal is closed by a logout after it. It closes THAT session only: another device signed in as the same account keeps working (the patient cookie already behaves like this: signing out deletes one row of `sessions`). Nobody is signed out by the deploy: a cookie without an id works as before, and the table starts empty. The listing outlives every copy: `max(the cookie's own exp, now + the session length, 30 days) + 1 day`, and every write deletes the rows past it. If the table cannot be read, the cookie is not checked (the gate already falls back to the role's permissions then, owner decision 2026-09-12), except for ids this process closed; any other failure of the check refuses the cookie. If the signing out cannot be written, the cookie is still cleared in the browser but the answer is a 503 `base_datos` (`revoked: false`) and the log says so — a copy stays valid and the caller must be able to tell. A portal-login installation (`TURNOS_STAFF_PORTAL_LOGIN=1`) has no staff cookie session (the gateway identity is per request) and its screens have no «Cerrar sesión»: nothing to close there. Deactivating an account already ended its open sessions on the next request (`permissions.access_for`); that stays pinned. Not in this change: changing a password does not sign the other devices out (a stateless cookie cannot be listed; it would need an issue time in the token and a per-account cut-off), and a session lineage forked before the deploy (a copy renewed before the deploy by the victim) is not closed by a logout after it — only changing `TURNOS_ADMIN_SECRET` signs everybody out.
Why: hospital TASK-55, found by the journey J28 (its «known limit»): on a shared reception computer the cookie copied before «Cerrar sesión» kept working until its 30-day expiry · Rejected: an epoch per account (one column, but signing out on one computer would sign out every device of the account), server-side staff sessions like the patient's (a row per issue and renewal, every `_mint_token` caller and ~80 test files issue sessions by signing, and the existing cookies would either all be signed out or stay unlistable), short-lived access cookies with refresh (a new session model for one finding) · Undo: revert the commit; the table stays, and the reverted verifier ignores it, so cookies signed out meanwhile work again until they expire (`TURNOS_ADMIN_SECRET` rotation signs everybody out) · Cost: one primary-key read per verified cookie (two on a panel screen: the navigation middleware and the gate), one new table, the logout is a database write · By: agent (technical choice inside TASK-55).
