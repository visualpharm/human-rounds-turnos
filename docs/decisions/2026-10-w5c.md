## 2026-10-26 · Moving live patient requests to another installation: the request and its history, nothing else, and a taken slot is a conflict
Decided: `scripts/fixes/requests_transfer.py` carries the pending requests and the approved ones still ahead from one installation to another (pinamar.humanrounds.org → salud.pinamar.gob.ar). The file holds an allowlist of the request's own fields — patient (DNI, name, birth date, sex, contact), service, center, doctor, time, state, who resolved it, the patient's note, confirmation and reminder marks — and never the order file or its AI reading, the other installation's HSI ids, the confirmation token or attendance; a cancelled, rejected or past request does not travel. No patient account is created: the portal login opens the account by DNI and `list_by_dni` shows the request. Imported rows carry no `hsi_status`, so no HSI retry picks them up; the desk loads them like any other. · Why: Salud, 26.10 (the reference-deployment counterpart, WA): «Copiarlos a salud.pinamar.gob.ar» — 6 real appointments given on the test site keep their slots on the municipal one, which opens 27.10 at 12:00 · Undo: on the target, the rows the run created (`idem_key` starting with `traslado:`); the script changes no table, revision or route · By: Salud (copy them), agent (the allowlist, no patient account, the key, one transaction per request — technical choices inside the request).

## 2026-10-27 · Moving live requests: the plan sees every conflict before `--apply`, a database error prints no patient data, the import refuses to run on the source installation
Decided: the review of `scripts/fixes/requests_transfer.py` (the product owner's hub, 27.10, items a–e) is taken whole. (a) The plan, so the dry run too, marks as a conflict an approved request whose (doctor, time) is taken by the rule of `booking_requests_doctor_slot_uniq` — approved, not an overbooking, same `assigned_doctor_id` and `appointment_at` — on the target database or earlier in the same file (the file's first request keeps the slot); the unique index stays the last guard against a race. (b) `--apply` catches `psycopg.Error` per request and prints only its id, the error class, the SQLSTATE and the constraint name (the driver message quotes the failing row: DNI, name, contact); the request's transaction rolls back whole; a row-level error (integrity or data) is counted in `errores` and the run goes on, any other database failure (connection, permissions, schema) stops it and counts the rest as `sin_intentar`; exit code 3; a second run finishes what is left. (c) A file value that does not parse (a birth date, a time, an id) is named by request id and field, never quoted, and a time without a zone is refused. (d) The plan checks the live catalog — `catalog.live_ids`: not switched off or deleted, and for doctors not waiting for onboarding — not `known_ids`; a request to a switched-off or deleted service, center (the same reason, added) or doctor is a plan conflict (`…_deshabilitado`, told apart from `…_no_esta_en_el_catalogo`). (e) Each installation names itself by the host of its `TURNOS_PUBLIC_ORIGIN` (`config.installation_host`, environment and .env only); the export writes that host as the file's origin (`--origin` is optional and must agree), and the import refuses on the installation named in the file, on any request of the file that exists here under its own id with the same DNI and creation time (a wrong origin cannot hide the source), and on an installation with no origin; the plan also lists a request the target already holds under another key (same DNI, service and time, among its pending and approved ones) and a repeat inside the file. Hardening from the critic round: a row this script made (`traslado:` key) is not a source sign (its id may coincide by chance with the source's); both stored doctor ids (`assigned_doctor_id`, `slot_doctor_id`) must be live; the slot rule reads any non-NULL doctor id like the index; the file's `status` is never echoed; a database or catalog failure while the plan is made prints its class only and exits 3. · Why: Product owner's review of the branch, 27.10 10:22 (Teams): «a, b, c, d, e — all of them»; he lands it after the Basic Auth branch · Rejected: an `--allow-source` override (it would defeat the check); comparing only the origin text typed at export (a typo hides the source) · Undo: revert the commit; the script changes no table, revision or route · By: Product owner (items a–e), agent (the stop-or-go rule, the second source sign, centers in (d), exit code 3 — technical choices inside the review).
