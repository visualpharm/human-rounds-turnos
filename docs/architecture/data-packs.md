# Layered data packs

Phase 2a of the open-source rework (`~/.claude/plans/large-rewrok-before-open-robust-chipmunk.md`), 2026-07-30. Historical migration sections remain below. **Current correction (2026-08-20):** the real Pinamar pack has been evacuated from this public tree into a dedicated private repository and verified production volume. The bundled default is `global,example-town`; real deployments opt into private packs with `TURNOS_PRIVATE_PACKS_DIR`, `TURNOS_REQUIRED_PACKS`, and an explicit `PACK_CHAIN`.

## Why

Sana Turnos was Pinamar-hardcoded. `sitedata.py` (2026-07-16) already made the data package swappable as ONE directory (`webdata/` or `TURNOS_WEBDATA_DIR`). That's enough for "one town, one checkout" but not for "share a national specialty taxonomy across every town" — a province shouldn't have to retype the country's DNI/phone rules, and a new municipality shouldn't have to retype the national list of medical specialties to add one local entry. Layered packs let a deployment compose several locality levels instead of copying everything into one flat directory.

## Layout

```
packs/
  global/                   L1 — engine-agnostic medical content
  ar/                       L2 — Argentina (phone/DNI/timezone/currency/emergency, trusted domains, endpoints)
  ar-b/                     L3 — Buenos Aires province (MSD institution mapping, trusted domains)
  example-town/             L4 — Sampleton, the scaffold for a new town

<TURNOS_PRIVATE_PACKS_DIR>/
  ar-b-pinamar/             L4 — private Pinamar reference deployment (not bundled)
    centers/<slug>/         L5 — per-center override packs, wired (phase 3, 2026-07-30) — see "Center packs (L5)" below
```

Each pack has a `pack.json`:

```json
{
  "id": "ar-b-pinamar",
  "level": 4,
  "parent": "ar-b",
  "language": "es-AR",
  "name": "Pinamar",
  "description": "..."
}
```

`level` is documentation (1-5, matching the directory depth above); the actual resolution order comes from the CHAIN (below), not from re-deriving parents at runtime — `parent` is metadata for a future admin "choose your chain" screen, not consulted by `data_packs.py` today.

## Two modes

- **Pack mode** — the default the moment `packs/` exists on disk. The active chain is `config.get("PACK_CHAIN")` (comma-separated ids), defaulting to `global,example-town`. Optional ids without a valid pack are dropped; ids named in `TURNOS_REQUIRED_PACKS` fail boot closed when absent or corrupt.
- **Legacy mode** — `TURNOS_WEBDATA_DIR` set, or `packs/` missing entirely. Behaves exactly like `sitedata.py` did before this slice: one directory, no layering. `TURNOS_WEBDATA_DIR` always wins over pack mode — this is what keeps `test_sitedata_dir.py`'s Sampleton fixture working (`packs/example-town/`, self-contained on its own even in legacy mode — see "retiring `webdata-ejemplo/`" below), and what a one-off checkout pointed at a single custom directory still gets.

`sitedata.py` is now a thin compat shim: `sitedata.path(fname)` delegates to `data_packs.resolve_path(fname)`, so every one of its ~15 existing call sites (`catalog.py`, `patient_web/site_*.py`, `booking_requests.py`, `preparation.py`, `calendar_feed.py`, `remedies.py`, `msd_data.py`, `reports.py`, `system_status.py`, …) kept working with zero changes. `sitedata.webdata_dir()` stays exactly what it always was — the single legacy directory, never pack-aware — because a couple of callers (`system_status.py`'s Sistema page) want "the one webdata-shaped directory to display a name for," not "the file that's actually active right now."

## Install-owned town packs — durable across rebuilds (Tier 6)

The repo's `packs/` (what `packs_dir()` returns, and where `global`/`ar`/`ar-b`/`example-town` live) is **baked into the image** — fine for the engine's bundled public packs, fatal for a clinic's *own* data. The first-run installer ([setup-wizard.md](setup-wizard.md)) scaffolds a brand-new town from the deployer's entered name, and that scaffolded pack is the clinic's private install-owned data, not engine content. Writing it into the image-tree `packs/` made it vanish on the next rebuild (a new release repopulates `packs/` from the build context); `manifest()` stopped finding it, `active_chain()` dropped it, and the site fell through to an empty chain. Detail + the fix → [install-owned-town-packs-live-on-the-volume.md](../solutions/deploy/install-owned-town-packs-live-on-the-volume.md).

Three pieces, all building on the reviewed private-pack resolver (no new resolution semantic):

- **`install_packs_dir()`** — the durable install-owned root a scaffolded town is written to: a configured `TURNOS_PRIVATE_PACKS_DIR` wins, otherwise `<data_dir>/packs` ON THE PERSISTENT VOLUME (`/app/data/packs` in prod; `TURNOS_DATA_DIR` overrides the data dir the same way every boot setting is read). Deliberately NOT `packs_dir()` (the image tree). `data_dir()` is the same volume `/app/data` covers at runtime.
- **`write_inventory(directory)`** — the strict inverse of `_inventory_entries`: stamps `INVENTORY.json` (path + size + sha256, regular files only) for a pack the installer just created, so the required-pack readiness gate admits it on the next boot instead of failing closed on a missing inventory.
- **The wizard's commit** writes the scaffolded town into `install_packs_dir()` with a frozen inventory, then registers three boot keys together in the effective `.env` via `config.save_env_keys` (the only `.env` boot-key writer — process/`.env`-only by design, never the DB): `TURNOS_PRIVATE_PACKS_DIR=<install_packs_dir()>`, `TURNOS_REQUIRED_PACKS=<slug>`, and `PACK_CHAIN=<prefix>,<slug>`. The chain moves WITH the required pack so a locked-config restart (`TURNOS_CONFIG_LOCK=1`, DB overrides ignored) still serves the town instead of the bundled public default — otherwise the gate would validate a private pack the chain never serves. `PACK_CHAIN` is also written to the DB (via `config.guardar`) for normal-operation admin edits; under the lock the boot-key copy wins.

Reuse, not new machinery: a scaffolded town resolves exactly like any other private pack — `_pack_dir(slug)` → `_private_pack_dir(slug)` (verified + inventory-valid) → `manifest()` → `active_chain()` → `resolve_path()`. Because it is registered REQUIRED, `verify_required_packs()` (the pre-listener gate in both legacy and ASGI boot) admits it on every later boot, and **fails closed** if the volume is ever unmounted (`private root invalid`), partially seeded (`directory missing`), or byte-tampered (`inventory checksum mismatch`) — never a silent fallback to a bundled public copy or an empty site. Optional invalid private packs keep their degrade-not-crash fallback; bundled public packs and the default chain are unchanged. Proven synthetic (no real clinic data) in `tests/test_install_owned_packs.py`: create town → simulated rebuild (image tree repopulated, volume kept) → same validated pack resolves.

## Resolution: override vs merge vs compose

Three files can need three different composition rules, so `data_packs.py` exposes all three and callers pick:

- **`path(fname)` / `resolve_path(fname)` — whole-file OVERRIDE.** The highest-level pack in the chain that HAS the file wins, entirely; lower levels become invisible the moment a higher one defines the same filename. For files that describe ONE deployment's concrete reality, where "inheriting a base version" makes no sense: `sitio.json` (site identity), `centros-salud.json`, `servicios.json`, `medicos.json`, `msd_turnos.json`, review/gallery/photo JSON. A town pack (or a center pack, see "Center packs (L5)" below) supplies the WHOLE current file, not a diff against some ancestor.
- **`merged(fname, list_key, id_key)` — id-keyed list MERGE, a generic primitive.** Every pack in the chain that has the file contributes its list, low level first; an item whose `id_key` was already seen REPLACES it in place (keeps the base's ordering, doesn't move it to the end), a new id gets appended. Proven and independently tested (`tests/test_data_packs.py`'s `TestMerged`) but with no direct production caller — `compose()` is built on the same shape, for the closed set of files that actually need it (below).
- **`compose(fname, center=None)` — REGISTERED composable files only (phase 3, 2026-07-30).** `especialidades.json`/`clusters.json` are the two files in `data_packs._COMPOSABLE`. Default behavior is `merged()`'s (low level → high level, higher level wins per id) — PLUS two rules the flat `merged()` primitive doesn't have, both needed to fix the phase-2b revert below: a pack's `pack.json` can declare `"compose": {"<fname>": "replace"}` (from that pack's level down, every ancestor is invisible for that one file — `packs/example-town/pack.json` uses this), and an entry `{"<id_key>": x, "_removed": true}` tombstones id `x` out of the composed result at any level. Every file NOT in `_COMPOSABLE` keeps whole-file override via `path()` — this is a closed list, not a general escape hatch.

`catalog.specialties()` and `site_catalog._clusters()` — the two real readers of these files — go through `compose()`, not `_load_json()`/`path()`.

## The pilot: `especialidades.json` + `clusters.json`

Moved OUT of `webdata/` into `packs/global/` — the two files least tied to Pinamar specifically (a specialty→cluster taxonomy, not locality data) and, conveniently, not in the render path of the three golden pages, so this pilot could prove the override chain end to end with zero risk of an observable behavior change. ### The `ar-b-pinamar` legacy fallback

Since Pinamar's locality data hasn't been sorted into `packs/ar-b-pinamar/` yet, `resolve_path()` has one special case: if `ar-b-pinamar` is part of the active chain and NO pack in the chain has the requested file, it falls back to `webdata/<fname>` — exactly where `sitedata.py` would have looked before packs existed. This fallback is scoped to that one pack id on purpose: `example-town`'s chain (`global,example-town`) never triggers it, which is what keeps the genericity test (`PACK_CHAIN=global,example-town` renders zero "Pinamar" strings on the home page) honest — nothing in that chain can leak Pinamar's `webdata/`.

As the mass-migration agent moves files out of `webdata/` into `packs/ar-b-pinamar/`, each moved file simply starts resolving from its new home — present in the chain, so found before the fallback triggers — with **zero code changes to `data_packs.py`**. Once every file has moved, the fallback becomes dead code; deleting it is a good "migration complete" signal for that slice.

### `packs/example-town/`

A self-contained copy of `webdata-ejemplo/`'s 7 files (`centros-salud.json`, `clusters.json`, `especialidades.json`, `estudios-preparacion.json`, `medicos.json`, `servicios.json`, `sitio.json`), activated with `PACK_CHAIN=global,example-town`. It deliberately carries its OWN `especialidades.json`/`clusters.json` instead of falling through to `packs/global/`'s (Pinamar-derived) versions: Sampleton's curated subset doesn't line up 1:1 with Pinamar's full taxonomy (e.g. "Nutrición" maps to a different cluster in each), so relying on the shared global pack would have silently changed Sampleton's own behavior. `webdata-ejemplo/` itself is untouched — it keeps serving `test_sitedata_dir.py`'s legacy-mode (`TURNOS_WEBDATA_DIR`) fixture. The duplication between `webdata-ejemplo/` and `packs/example-town/` is a known, intentional gap for now; deduplicating (retiring one in favor of the other) is mass-migration-agent work, not this slice's.

## Cache-key contract

Every mtime cache built on top of `path()`/`resolve_path()` MUST key by the RESOLVED PATH, never the bare filename — a filename-only key can't distinguish "the file the global pack ships" from "the file a higher pack overrides it with," so a pack-chain change (or a file moving between levels) would silently serve a stale cross-pack collision instead of invalidating.

- `catalog._JSON_CACHE` and `site_base._CACHE` were fixed in this slice (both keyed by bare filename before).
- `site_identity._CACHE` was already correct (already keyed by the resolved `sitio.json` path).

## L5 (per-center) packs — wired (phase 3, 2026-07-30)

`active_chain(center=None)` / `resolve_path(fname, center=None)` accept an optional center slug: when given, and the chain's highest pack has a scaffolded `centers/<slug>/pack.json`, that pack is appended as the chain's highest-priority segment (a real compound id, `"<town-id>/centers/<slug>"` — `_pack_dir()` just joins path components, no special-casing needed). No `center`, or an unscaffolded one, and the chain is exactly what it would have been without this — same degrade-not-crash rule as every other chain entry. `path()`-style whole-file OVERRIDE, not `merged()`/`compose()`.

The one real pack: `packs/ar-b-pinamar/centers/hospital-pinamar/` overrides `estudios-preparacion.json`'s `laboratorio-sangre` fasting note (`preparacion-centro.json`) with the fact that the Hospital's own lab sign doesn't publish it online — a documentary note (`estudios-preparacion-meta.json:_meta.nota_laboratorio_hospital_pinamar`) that had been sitting unwired since the file-rename slice. `site_preparation._center_prep_overrides(center)` / `_prep_section_html(s)` apply it only when the rendered service's own `centro` matches — proven by `tests/test_data_packs.py`'s `TestCenterPackHospitalPinamar` (the override wins for `laboratorio-hospital`/`extracciones-de-laboratorio-pinamar`, both at `hospital-pinamar`, and does NOT leak to `extracciones-ostende`/`extracciones-valeria`, the same study at other centers). `tests/test_golden_pages.py` stays byte-identical: its one golden service page (`radiografia-hospital`) matches a different `estudios-preparacion.json` entry, so the override never touches it.

## `packs/ar/` — country-level data (phase 2b slice 1, 2026-07-30)

## `packs/ar-b-pinamar/` round 2 — the pure-JSON drain (phase 2b slice 6, 2026-07-30)

Moved OUT of `webdata/`, unchanged (still Spanish-keyed, same key-rename-pending status as round 1): `servicios.json`, `medicos.json`, `msd_turnos.json` (the committed snapshot — `data/msd_turnos.json`, the LaunchAgent-refreshed runtime dump, is untouched, still not in git), `centros-info.json`, `centros-galeria.json`, `centros-resenas.json`, `resenas-analisis.json`. All seven were already read exclusively through `sitedata.path()`/`data_packs.resolve_path()` (`catalog.py`, `patient_web/site_*.py`, `calendar_feed.py`, `preparation.py`, `booking_requests.py`, `system_status.py`, `reports.py`, `msd_data.py`, `scripts/tools/seed_hsi_medicos.py`) — moving the files was the entire runtime-code change.

**Real bug found and fixed along the way**: `admin-content.js` fetched these (plus `especialidades.json`/`clusters.json`/`centros-salud.json`, moved in earlier slices) via a hardcoded `/webdata/<file>.json` URL for its admin-editor "compare to original" `<details>` view — a URL that 404s the moment the backing file leaves `webdata/`, since `/webdata/` is a literal static-serving prefix (`services.legacy_static.PUBLIC_STATIC_PREFIXES`), not pack-aware. This means the compare view for `centros-salud.json`/`especialidades.json`/`clusters.json` had **already been silently broken** since the slices that moved those three; nothing caught it because no test exercises that live `fetch()`. Fixed at the root instead of file-by-file: the existing `/data/<f>` compat route (originally "webdata/ moved out of the app root, keep the old URL") is now **pack-chain aware** — it resolves through `sitedata.path(rel)` (checking both `webdata/` and, if the checkout has one, `packs/` as allowed physical roots) instead of a hardcoded `WEBDATA_DIR` join, then rewrites `self.path` to wherever the file actually resolved before handing off to `SimpleHTTPRequestHandler`. The route now lives in `services.legacy_static.LegacyStaticMixin`. `admin-content.js`'s five `/webdata/<f>` fetches became `/data/<f>` (bumped `?v=39` → `?v=40`, cascaded into the two tests that pin that literal). This also means **binary/photo assets can move into `packs/` in a future slice without another transport change** — the compat route is now generic, it was only ever pinned to `webdata/` by accident of history.

`data_packs.py` gained a small public accessor, `packs_dir()` (returns `_PACKS_DIR`), for that boundary check — the only caller outside this module that needs the packs root path, so it stays a thin getter rather than exposing the private constant directly.

Also fixed while sweeping for stale hardcoded paths (mechanical, no behavior change beyond "stops crashing"): `scripts/import_detalle_turnos.py` (was ALREADY broken — its `especialidades.json` read hardcoded `webdata/`, dead since the pilot slice moved that file to `packs/global/`; now reads/writes all three files via `sitedata.path()`), `scripts/fetch_resenas.py` and `scripts/analizar_resenas.py` (same latent break on `centros-salud.json`, since the round-1 slice), `scripts/fetch_brila_photos.py` (`centros-galeria.json`), `scripts/build_medico_photos.py` and `scripts/discover_new_medico_photos.py` (`medicos.json` — the latter's `_doctors_from_parent()` also stopped hardcoding `HEAD^:webdata/medicos.json` for its `git show` diff, now derived from the resolved path so it keeps working across future pack-chain moves instead of silently returning an empty "no prior doctors" set). **Still in `webdata/`, NOT moved this slice — the binary/public-URL problem** (see "What the mass-migration agent does next" below): `photos.json`, `featured-medic-sprite.{json,webp}`, `doctor-photo-sprite.{json,webp}`, `medico-photo-sprite.{json,webp}`, `medico-fotos.json`, `clinic-maps-urls.json`, `brila-generation-results.json`, and the photo/research directories `centro-photos/`, `centros-brila-info/`, `doctor-photos/`, `medico-photos/`, `photos-cache/`, `fuentes/`, `talleres/`. Reason, found while auditing rather than assumed: `patient_web/site_*.py` (and `servicios.json`'s own `foto` field values, e.g. `talleres/adolescentes-ostende.jpg`) build PUBLIC image URLs as literal `/webdata/<path>` strings — `/webdata/` is directly public (`legacy_static.PUBLIC_STATIC_PREFIXES`), served straight off disk by `SimpleHTTPRequestHandler(directory=ROOT)`, no route in between. ## Wiring `especialidades.json`/`clusters.json` through `merged()` — ATTEMPTED and REVERTED this slice (phase 2b slice 11, 2026-07-30)

Tried the mechanical version of item 2 below: `catalog.specialties()` → `data_packs.merged("especialidades.json", "especialidades", id_key="nombre")`, `site_catalog._clusters()` → `data_packs.merged("clusters.json", "clusters", id_key="id")`. **Full suite stayed green (1793+440) — and it was still wrong, caught by manually inspecting the actual merged output, not by a test.**

The bug: `merged()` composes ADDITIVELY across the WHOLE chain, low-to-high. For Pinamar's own chain (`global,ar,ar-b,ar-b-pinamar`) this is a no-op — no pack above `global` has its own `clusters.json`/`especialidades.json` yet, so the merge degrades to reading `packs/global/`'s file alone, identical to the old `path()` behavior. But `packs/example-town/`'s WHOLE REASON for shipping its own `clusters.json`/`especialidades.json` (see the pilot section above) is that it's a deliberately curated SUBSET that does NOT want to inherit Pinamar's full taxonomy — under `path()` (override), its own file fully replaced `packs/global/`'s. Under `merged()` (compose), `PACK_CHAIN=global,example-town` pulled in **all 13 of `packs/global/clusters.json`'s Pinamar-derived clusters PLUS example-town's own 5**, expanding Sampleton's cluster list from a curated 5 to 13 — verified directly: `PACK_CHAIN=global,example-town python3 -c "import data_packs; print([c['id'] for c in data_packs.merged('clusters.json','clusters',id_key='id')])"` returned `endocrino`, `gineco`, `odontologia`, `otorrino-fono`, etc., none of which exist in Sampleton's own service catalog. None of this shows up as a test failure: `TestExampleTownChainIsGeneric` only asserts zero literal "Pinamar" strings and that SOME real Sampleton content renders — it never asserts an exact cluster count or set, so a silent content leak passes clean. This is precisely the failure mode the pilot slice's own docs warned about ("relying on the shared global pack would have silently changed Sampleton's own behavior") — just triggered by a LATER slice's mechanical wiring instead of the original one.

**Reverted both call sites** (`catalog.specialties()` still reads `packs/global/especialidades.json` via `_load_json()`; `site_catalog._clusters()` still reads via `_load()`) rather than ship a behavior change with no test catching it. `merged()` itself is correct and stays as designed (proven by `test_data_packs.py`) — the bug is that a flat whole-chain compose is the WRONG semantic for a town pack that wants to fully replace a lower level's taxonomy while a national/provincial level (which doesn't exist with real content yet) is meant to ADD to it. At the time: "not solved, flagged for real design work — `merged()` (or a caller) needs a way to say 'compose everything EXCEPT stop inheriting at level N'". See the section below for how this got fixed.

### `especialidades.json`/`clusters.json` through `compose()` — FIXED (phase 3, 2026-07-30)

Built exactly the escape hatch this postmortem called for, as a `pack.json` flag: `"compose": {"<fname>": "replace"}` (see `compose()` in "Resolution: override vs merge vs compose" above). `packs/example-town/pack.json` now declares it for both `especialidades.json` and `clusters.json` — from that pack's level down, `compose()` ignores every ancestor for those two files, so Sampleton's curated 6-specialty/5-cluster subset stays isolated from `packs/global/`'s 40/13 exactly like `path()`'s old override behavior did, while Pinamar's own chain (where no pack above `global` has its own copy of either file yet) degrades to reading `packs/global/`'s file alone — identical bytes to before. `catalog.specialties()` and `site_catalog._clusters()` now call `compose()`. Also added, generalizing the "id-keyed replace" contract this revert exposed as too rigid: a `{"<id_key>": x, "_removed": true}` entry tombstones id `x` out of the composed result, "replace" or not — not something this revert needed, but the natural next gap once a pack can both extend AND fully replace a taxonomy.

This time the test this postmortem asked for exists: `tests/test_data_packs.py`'s `TestCompose.test_replace_hides_every_ancestor_for_that_file` asserts the exact SET a "replace" pack produces (not just an absence of "Pinamar" strings), plus `TestGoldenPagesPinamarChain`/`TestExampleTownChainIsGeneric` (unchanged, still green) prove neither real chain's rendered bytes moved.

## Overlay legacy-key-alias layer (phase 2b slice 16, 2026-07-30)

## Private roots and required-pack readiness (Tier 6 slice 0, 2026-08-10)

`TURNOS_PRIVATE_PACKS_DIR` is an optional root whose valid pack replaces the
same public pack id. With it unset, resolver behavior is unchanged. An
optional private directory with an invalid manifest, inventory, checksum, or
symlink boundary is ignored, so the public pack retains the existing
degrade-not-crash behavior. Optional eligibility is cached by a whole-tree
stat stamp; required packs still perform their definitive check once at boot.

`TURNOS_REQUIRED_PACKS` is a comma-separated boot gate. If it names a pack,
`data_packs.verify_required_packs()` runs before the legacy server binds (and
therefore before that process can accept traffic). Both readiness knobs are
read only from the process environment or effective `TURNOS_ENV_FILE` (process
wins); they intentionally never consult DB Settings, so the gate remains
ahead of schema migration. `TURNOS_CONFIG_LOCK=1` keeps the same process-env
winner without opening a DB path. A
configured private root makes each required id private-only: a missing mount
never falls back to a bundled copy. Without a private root, a required public
pack is still valid for self-contained installations.

ASGI mode calls the same verifier synchronously before worker supervision,
composition import, background-service startup, or the single Uvicorn
listener. A failed readiness gate therefore leaves no serving process alive.

The gate validates a real, contained pack directory; matching `pack.json` id;
and strict `INVENTORY.json` (`{"files":[{"path","size","sha256"}]}`) coverage.
Inventory paths are relative, unique, non-symlinked regular files and exactly
match the pack tree (except the inventory itself). Boot re-hashes every JSON
file plus a deterministic sample of up to eight binary assets. Any failure is
fatal with value-free diagnostics; optional packs remain non-fatal.

`/webdata/<asset>` and `/data/<asset>` retain their public URLs. Public-pack
files keep the stdlib static handler exactly as before. A verified private
root outside the checkout is served through root-dirfd component descent with
`O_NOFOLLOW`, rejecting traversal, symlink escape, and a directory swap after
the initial realpath check.
