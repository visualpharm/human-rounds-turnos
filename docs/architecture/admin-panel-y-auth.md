- **A 401 is NOT proof the session died (2026-07-27, product owner: "i get disconnected from admin all the time" — do not relitigate).** The `st_admin` cookie is a 30-day signed token (since 2026-10-28 its check also reads one row of `admin_session_revocations`, and an unreadable table signs nobody out), so it almost never actually expires; what dumped people to the login screen was the CLIENT. `boot()` in admin.html fell through to `showGate()` on ANY stumble after a valid `whoami` — a module throwing, `/api/admin/requests` not answering 200, or a 401 from something else entirely (the shared pre-launch Basic Auth that the browser stopped resending; reproduced live on prod with a perfectly valid cookie). Now: `whoamiBoot()` retries and returns identity / `'sin-sesion'` (our own JSON `{"error":"no_autenticado"}`) / `'error'`, and **only `'sin-sesion'` shows the login**; every post-whoami step runs in its own try (`paso()`), and a failed queue fetch paints "No se pudo cargar la cola · Reintentar" instead of asking for the password. `mostrarGate()` is the raw renderer (only `boot()` and `api()` call it, after confirming); the public `window.showGate()` — which ~20 modules call the instant they see a 401 — asks `sesionMurio()` (re-checks whoami; anything that isn't our JSON 401 = the session is alive) and otherwise just toasts. **The pre-launch Basic Auth STAYS in front of the panel** — exempting `/admin` + `/api/admin/*` was tried and reverted the same day: the page opened but its ~20 `.js` were still walled, so anyone without the shared credential got a half-loaded panel (exempting the assets too = exempting the whole site). It never logged anyone out anyway: that 401 arrives without our JSON and `sesionMurio()` now tells them apart. Both serving modes share ONE decision (`site_auth.authorize`): `server.py`'s `check()` owns dark mode, while `app/auth/site_auth_middleware.py` is the outer native-ASGI boundary, so an `/api/...` endpoint is no more reachable than `/` while the gate is armed. - **Passkeys (WebAuthn) for the panel: `passkeys.py` + canonical `static/platform/passkeys.mjs` (updated 2026-09-04).** The admin login and Account controllers import named exports through `window.SANA_STATIC`; the classic file and `window.SanaPasskeys` global are physically absent. Register from Mi cuenta, then "Entrar con passkey" at the gate — no password, no 6-digit code. The maintained `py_webauthn` library owns attestation, COSE parsing, signature validation, rpId/origin and user-presence checks; historical ES256/RS256 JSON rows are converted to library COSE only at that boundary. There is no in-house CBOR, COSE, curve, DER, or signature fallback. Routes under `/api/admin/passkeys/*`: `register-options`/`register` (session required), `GET` list, `delete`, `reset`, and `login-options`/`login` — the last two run WITHOUT a session by definition (that's why the site_auth exemption above matters). A challenge is HMAC-signed for integrity and returned only to the browser, while PostgreSQL stores only its SHA-256 digest plus purpose, expiry and registration owner. Atomic `UPDATE ... RETURNING` consumption rejects replay across ASGI processes; expired and old consumed rows are cleaned on issuance. Registration requires the same authenticated account that requested the challenge. **rpId comes from the request Host**, so in dev you MUST use `http://localhost:7700/admin` — WebAuthn accepts `localhost` but never a bare IP. The credential alone identifies the account (`db_auth.passkey_by_credential` → `usuario`), and the ROLE comes from the account, never from the key — an operator marked `activo=false` doesn't get in with their passkey. Table `passkeys` (usuario, credential_id, public_key jsonb, sign_count, nombre); a nonzero counter advances atomically or the login fails closed, while synced passkeys that legitimately report zero retain the existing behavior. Reset: each person removes their own from Mi cuenta; an **admin wipes another account's from Usuarios** ("Quitar las passkeys" next to Quitar 2FA — the lost-phone exit, applied immediately, not on Guardar). The CDP virtual-authenticator E2E is `tests/e2e/passkeys.spec.mjs`; this audit row remains open until the complete password+TOTP+passkey journey, session window, and role matrix are proven.

### Roles and permissions: the panel decides by permission, never by role name (2026-10-23)

The access model lives in `app/core/permissions.py` (`PERMISSIONS`, `BUILTIN_ROLES`,
the route → permission map consulted by `admin_auth.evaluate_admin_gate`).
Built-in roles: `admin` (everything), `admisionista` (solicitudes, cola,
crear_turnos, pacientes), `gestor_agendas` (admission desk + `medicos`),
`medico`, `reportes`.

- **Adding a role:** the usual new role is a preset — an entry in
  `permissions.BUILTIN_ROLES` (seeded into `roles`; the account keeps its slug
  in `operator_access.role_slug`, `operators.role` stays on its base value), no
  CHECK change. Only a fifth value of `operators.role` itself touches FIVE
  places (`admin_users._ROLES`, a forward Alembic revision on
  `operators_role_check` with `schema_model.py` and `schema-head.txt`,
  `db_operators._OPERATOR_TABLE_ROLES`, `permissions.LEGACY_ROLES`, `applyRol`

  (`db_slots.hold_acquire` returns False), see `wizard-y-servicio.md`.
- **A map value may be «any of»:** a `frozenset` of permission ids admits a
  holder of ANY one of them. Always test it with `permissions.holds(required,
  held)` — the gate, `app_modules` section visibility and
  `test_roles_parity.py` all do. Today's only case:
  `GET /api/admin/doctors/stats` = `{medicos, reportes}` — the Médicos list

### Médico = usuario — one entity, one list (2026-10-19)

The product owner (m585916): «when we create a doctor, we should automatically create a
user … don't make administrators create medics twice». **Do not relitigate.**

- **One create, one transaction.** `admin_content.create_item("medicos")`
  writes the catalog overlay row and calls
  `admin_users.provision_doctor_account(doc, connection=…)` inside the same
  `catalog_schedule_lock` transaction; a failure on the account insert rolls
  the doctor back (`test_doctor_account_unify.test_injected_account_failure_leaves_no_doctor`).
  The account is rol médico, inactive, «sin invitar», username
  `nombre.apellido` in ASCII de-duplicated with a digit
  (`admin_users.doctor_username_base`), random unrevealed password.
- **One account per doctor is a database rule**: partial unique index
  `operators_doctor_id_uniq` (Alembic `0022_doctor_account` + `_SCHEMA_SQL`);
  a violation surfaces as `OperatorConflict("medico_con_usuario")`.
- **Account state** (`db_operators.operator_account_state`, served as `cuenta_estado`):
  `sin_invitar` → `invitado` (`operators.invited_at`, or an active account
  whose credentials were handed over) → `ingreso` (`last_access`) →
  `perfil_completo` (`onboarding_completed_at`); `activo` stays separate.
- **Invitation needs no field** (m585886). `admin_users.invite_account`
  activates, stamps `invited_at`, and with any known email sends the
  invitation by itself; without one (or when Mailgun fails) it returns the
  one-use link to copy. Invitation links last 7 days
  (`staff_access_email.INVITE_HOURS`), reset links 24 h — same
  `admin_reset_tokens` type with its existing `horas` argument.
  `POST /api/admin/content/doctors` with `_invitar: true` is «Invitar médico»;
  a plain create invites only when an email was typed. On a portal-login
  installation (`TURNOS_STAFF_PORTAL_LOGIN=1`) the email is the portal match
  and there is no link to copy, so «Invitar médico» without an email is a 400
  `{error, field: "email"}` before the doctor or its account is written
  (`admin_users.portal_email_missing`), the same refusal the list import gives
  per row; a plain create without an email still makes the `sin_invitar` doctor.
- **A doctor can also be an administrator (2026-11-02).** The site's
  administrator: «al ser médica no me deja agregarle ese perfil» — a gap, not a rule:
  the role change dropped `medico_id` and the doctor's account was hidden from
  Usuarios. Now the account of a doctor is promoted in place from the doctor's
  Usuario tab (the «Rol» row's «Administrador» checkbox, which saves on change
  with a `PUT /api/admin/users/<usuario>` and `{rol}`; a refusal unticks it and
  says why under the row, 2026-11-04): `edit_user` keeps `medico_id`
  whenever the effective role is `admin` (Usuarios sends `medico_id:""` for
  every non-doctor role and that no longer cuts the link); going to any other
  role still clears it. `operators_doctor_id_uniq` and `_guard_operator_doctor`
  cover `medico` and `admin`, so the doctor still has ONE account;
  `operator_by_doctor_id`/`operator_doctor_ids` ignore the role. The admin's
  agenda and portrait stay with the doctor, but the personal screens («Mis
  turnos», own-patients scope) key on `rol == "medico"`: an admin sees every
  patient through the admin screens and has no «Mis turnos» until it goes back
  to doctor. Disabling the doctor in the catalog deactivates only a `medico`
  account, never an administrator's. The last user-manager guard
  (`assert_user_manager_remains`) applies as usual.
- **Incomplete doctors stay private.** `catalog._validate_doctor` lets a new
  (or still-incomplete) doctor lack name, specialty and center and sets the
  derived `incompleto: true`; `catalog.doctors()` and the patient site's
  `merge_with_overlay` skip it, account code passes `incluir_incompletos=True`,
  `admin_list` includes it. A complete doctor keeps the strict validation (an
  edit can't unpublish it by clearing its specialty). A nameless doctor's id is
  `medico-<hex6>` and never changes.
- **Onboarding asks everything**: email is required; with no center the
  «Tu agenda» step asks for one (`needs_center`, `center_options`); the
  complete API answers 400 `{faltan:[…]}` until name, specialty, email and a
  center exist.
- **The panel (one place for doctors).** Médicos (`admin-content.mjs`) reads
  `/api/admin/users` once and maps it by `medico_id` into the «Cuenta» column
  (`admin-users.accountStateLabel`: Sin invitar / Invitado / Ingresó / Perfil
  completo / Inactiva); a nameless doctor reads «Médico sin nombre» and an
  `incompleto` one «Todavía no está en el sitio». «Invitar médico» beside
  «Nuevo médico» posts the create with `_invitar` and only the fields typed;
  «Nuevo médico» stays on the created doctor and shows the `cuenta` outcome.
  Every outcome — email sent to whom, or the link with «Copiar» — is painted by
  `admin-users.showInviteOutcome` (same copy path as «Copiar acceso»). The
  Usuario tab shows the account inline with Invitar (optional email),
  «Usuario y contraseña» (only `sin_invitar`), reset, 2FA reset and
  Desactivar; linking an existing user is only behind «Reparar vínculo» for a
  doctor with no account. Usuarios hides médico accounts that have a
  `medico_id` and never creates a médico (the role is not offered to a new
  user; the form links to Médicos).
- **Backfill**: `scripts/fixes/backfill_doctor_accounts.py` (dry run default,
  `--apply`): links an unlinked médico account matching by email or
  `nombre.apellido` login only when unambiguous, lists ambiguous ones and
  possible duplicate records (the login already belongs to an account linked
  to another doctor — pinamar had «martin-galvan» next to «galvan-martin»),
  skips generic `rol` entries («Enfermería», which also get no account on
  create), and creates the rest inactive «sin invitar». Idempotent; a doctor created meanwhile is
  counted under `carrera`. Each installation runs it once after upgrading.
- **The username travels with the link.** A copied invitation shows «Usuario»
  next to the link, and `/admin/reset-password` names the username of a valid
  token, read from the token row (`db_auth.admin_reset_token_username`), never
  from the query.
- **Deshabilitar a doctor deactivates its account** (`admin_content.delete_item`
  → `db_operators.operator_deactivate`), never deletes it. That kept account still
  holds the doctor's id, so a new doctor whose derived id is held by any
  account gets the next free suffix (`prueba-qa-borde-2`,
  `db_operators.operator_holds_doctor_id`) — the old account is never relinked.
