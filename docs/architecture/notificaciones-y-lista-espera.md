# Patient emails, reminders, cancellation, waitlist

Extracted from CLAUDE.md 2026-07-29 (verbatim). These are load-bearing decisions — **do not relitigate** what is marked as such. Read this file before touching the code it describes. (Naming note: the code was since renamed to English — `notifications.py`, `reminders.py`, `waitlist.py`, `email_mailgun.py`; the Spanish filenames below are the same modules.)

- **One email entry point, provider selectable (2026-10-20).** Every sender calls `notifications.mail.send(to, subject, text, html=None)`; the provider is the `email_transport` connector — Mailgun by default (`app/notifications/mailgun.py`), Mailjet with `CONNECTOR_EMAIL_TRANSPORT=mailjet` (`app/connectors/mailjet/mailjet.py`). The missing-key silent-skip contract applies to both. `send` is the bool of `notifications.mail.deliver`, which answers `sent`, `skipped` (configuration: no public origin, no provider, mail off, the outbound kill switch, missing keys) or `failed`; the day-before reminders call `deliver`, because they retry a failure (three tries per row per process) and never a skip (2026-11-10). Variables → [deploy.md](deploy.md).
- **All patient emails are multipart text+HTML (2026-08-01).** `mail.send(to, subject, text, html=None)` (was `email_mailgun.send`); ONE shared layout builder in `notifications.py` (`_html_layout` — table-based ~560px container, site name header, real `<p>` paragraphs, table-based primary button in the brand accent, muted footer) renders every patient email; the plain-text part is always kept and the missing-key silent-skip contract is unchanged. Never hand-build email HTML outside that builder.
- **The Pre-Consult interview is promoted in three places (2026-08-01):** a CTA button in the received + approved emails (via `booking_requests._entrevista_field`, best-effort), a SEPARATE day-before email while it's still pending (`reminders.tick_interview`, marked once via `booking_requests.interview_reminder_at`, same always-mark pattern as `recordatorio_dt`; the WhatsApp day-before reminder appends the link too), and the account surfaces (`/request/<id>` + my-requests list). Detail → [entrevista-previa.md](entrevista-previa.md).

- **The day-before reminder ASKS, and the answer arrives by two doors that share one path (2026-08-02).** Until now the "¿vas a poder venir?" only went out by WhatsApp, and the institutional Meta number is still in trámite — so nobody was being asked at all. Two things changed. (1) `db_booking.booking_requests_to_remind` now also selects `contact` and `confirm_token`: it did NOT select `contact`, so `notifications._whatsapp_reminder` read an empty contact and the WhatsApp message never went out even with a provider configured. (2) The reminder email carries the question with two one-click links — primary button "Sí, voy a ir", secondary link "No voy a poder ir" — pointing at `/appointment/confirm/<token>?r=si|no` (`appointment_confirm.py`, a new module; `confirm.js` on the client). **The token IS the authentication** (`booking_requests.confirm_token`, created lazily by `db_booking.booking_request_confirm_token` when the reminder goes out and never rotated — reforwarding must not break the link already sitting in the inbox), same trust model as `appointment_offers.token`: the person opening the reminder on their phone the night before has no session, and making them log in to say "sí" is exactly the friction that gets no answer. **No GET ever changes state** — a link scanner (mail client, corporate filter) fetches every URL in an email, and a GET that cancels would let a scanner free a slot nobody released; every change is a POST fired by `confirm.js`, and the ONLY automatic one is `?r=si` (`data-auto="si"`, one click for the patient). `?r=no` deliberately asks once before giving the appointment away. Both doors — the free-text WhatsApp reply and the email click — go through `confirmations.record`, so what gets saved (`confirmacion` + `confirmacion_canal`, `"whatsapp"` or `"email"`) and what a "no" does (cancel for real via the patient's own path, so the waitlist gets its offer) are identical. Someone who already said "sí" and then can't come gets the change-of-mind link on the same page; an expired token, a past appointment or a cancelled one each carry the next real step, never a dead end. Tests: `tests/test_appointment_confirm.py` (incl. "abrir el link no confirma nada"), `tests/confirm-link.test.mjs`, `TestRecordatorioPideConfirmacion` in `tests/test_notifications.py`. **Copy + symptoms CTA on the confirm pages (2026-08-03, phone testing feedback).** The already-confirmed H1 stopped narrating the past ("Ya nos confirmaste que venís" read as a lecture) — now plain present, "Confirmado: te esperamos" + the service/date line, same principle everywhere else this module talks about a done confirmation. That page also carries the "Contale al médico cómo te sentís" CTA (`appointment_confirm._interview_cta_html`, reusing `notifications._entrevista_cta`/`_interview_pending` — one check, not a second copy): a large primary button (same style as "Sí, voy a ir") while the pre-consult interview is still pending, a quiet "¿Cambió algo? Actualizá lo que le contaste al médico" link once it's done, nothing when intake doesn't apply — GET-only, never mutates. The bottom account link on every confirm page now says "Todos mis turnos", matching the emails (06971c2).

- **"Al calendario" next to the date/time, no login (2026-08-03).** The approved and day-before-reminder emails carry a one-click .ics download right after the appointment's date/time line — `notifications._calendar_ics_url(row, handler)` reuses `booking_requests.confirm_token` (lazy-mint, same `db_booking.booking_request_confirm_token` the "¿vas a poder venir?" link already mints — the token IS the authentication, same trust boundary, and a GET that only reads a date/service/center adds no new exposure over what that link already reveals) and points at `GET /appointment/<token>.ics` (`calendar_feed._token_ics`, a new route on the module that already owned every other `.ics`). Unlike `_confirm_url` this one does NOT go away once the patient answers "sí"/"no" to the day-before question — the calendar link stays useful for the appointment's whole life. The route re-checks the LIVE `estado` at download time (not whatever it was when the email went out): only an `aprobada` request with a `turno_dt` serves an event, so a cancellation after the email went out just 404s, never a stale .ics. Read-only by construction (a single `SELECT` on the token, no update) — a mail client/corporate scanner prefetching the link is harmless, same reasoning as the confirm page's GET. Event: 40-minute duration (was 1h) + a 30-minute-before `VALARM`, same shared `_event()` builder every `.ics` endpoint uses, so the whole calendar surface (patient feed, doctor feed, single-appointment download, this new tokened one) picked up both changes together. Tests: `tests/test_calendar_feed.py:TestTokenIcs`.
- **The account link is "Todos mis turnos" everywhere (2026-08-03).** Every patient email that links to `/my-requests` (received, approved, reminder) used to word it per-email ("Seguí el estado…", "Detalle y calendario…", "Detalle en Mis solicitudes…" — the "calendario" part went stale the moment the approved/reminder emails got their own dedicated "Al calendario" link above). One label now, everywhere: "Todos mis turnos."
- **Patient emails are four, and they're actually sent (2026-07-16): received, approved, rejected, reminder.** `notificaciones.py` (templates on top of `email_mailgun.py`, the same shared Mailgun; `_prep_lineas` = shared builder that inlines the FULL preparation instructions — fasting/steps/what to bring — never "check Mis solicitudes") sends: on SUBMITTING the request (`notificar_recibida` from `_create`: service, center, chosen preference, preparation), on approval (friendly appointment time, center, inline preparation), on rejection (reason), and **the day BEFORE the appointment** (`notificar_recordatorio`). The reminder is triggered by `recordatorios.py`: a daemon thread started in `server.py:main` (same watcher pattern; `TURNOS_REMINDERS_OFF=1` turns it off, `TURNOS_REMINDER_INTERVAL_MIN` default 30), `tick(now_utc)` pure and testable: only between 09–21 ART, looks up `db_booking.booking_requests_to_remind(mañana_ART)` (compares `turno_dt AT TIME ZONE América/Argentina` — never the raw offset) and ALWAYS marks `recordatorio_dt`, whether or not the email went out (no email → no re-scan). No email on the account or no `MAILGUN_API_KEY` → silent skip: **create/approve/reject NEVER break because of the email** (same contract as HSI). **Since 2026-07-24 the day-before reminder ALSO goes out by WhatsApp** (`notificaciones._recordatorio_whatsapp` — `app/notifications/send.py`'s `_whatsapp_reminder` today: to the request's `contacto` if it looks like a phone, via `otp_send.enviar_texto`; asks "¿Vas a poder venir? Respondé SÍ/NO" — the reply enters the chat webhook and the engine can cancel; no WA provider configured → silent no-op). **Delivery truth (2026-08-14 transport contract): Meta free text is the configured transport (TEST tier, not production-activated), and the reminder is BUSINESS-initiated — a free-text send delivers only inside a 24h window the patient happens to have open, so the reliable day-before reminder still needs an approved Utility template (runbook §5); the earlier "institutional Meta number still in trámite" notes (line above) described the pre-test-number state and are superseded — a Meta TEST number is configured today, production activation is not.** Tests: `tests/test_notifications.py`.
- **The waitlist sweep has a second mechanism, opt-in (2026-08-06, Tier 4 slice 5 — docs/roadmap/tier4-replatform-design.md, "Background daemon threads -> Postgres-backed queue").** `TURNOS_WAITLIST_QUEUE=1` swaps the daemon thread below for a `procrastinate` periodic task calling the SAME unmodified `waitlist.tick()`, against the SAME Postgres (no Redis, no second database) — see `waitlist_queue.py`. Default is OFF (unset) everywhere, so every deployment today is byte-for-byte unchanged; `waitlist.start()` is the one function that decides, and the two mechanisms are mutually exclusive by construction (never both started, proven by `tests/test_waitlist_queue.py::TestMutualExclusion`). procrastinate's own schema is applied lazily, exactly once, ONLY when the flag is on (never as part of the normal `db._connect()` boot path, never in the Alembic chain) — guarded against a concurrent-boot race with the same keyed `pg_advisory_xact_lock(hashtext(...))` idiom `db_booking.create_booking_request` already uses. In this pilot shape the worker runs in-process, in its own daemon thread. Tier 1.4's race guarantees are untouched: this slice only changes WHEN `tick()` is called, never what it does. Tests: `tests/test_waitlist_queue.py` (cron-cadence parity via `croniter`, mutual exclusion, schema lifecycle, and sweep parity proven twice — a manually-deferred job and the real periodic deferrer firing on its own, both reaching the identical state `tick()` produces).
- **A THIRD mechanism exists since 2026-08-08 (Tier 4 worker topology — the design doc's "Worker topology" section): a real worker process outside the web process.** `TURNOS_QUEUE_WORKER=1` (supervised subprocess spawned by `asgi_main.py`) makes the web process start NOTHING for the migrated sweeps — `worker.py` owns them: one procrastinate app, waitlist (`waitlist_queue.register`) + reminders (`reminders_queue.py` — `tick()` + `tick_interview()`, same body, same claim-CAS duplicate-send guards), HTTP `/health`+`/ready`, a `procrastinate_workers` heartbeat row, graceful SIGTERM. The three mechanisms (thread / in-process pilot / external worker) are mutually exclusive by construction — delegation is checked first in `waitlist.start()`/`reminders.start()`. A down worker never makes the web app unhealthy: sweeps degrade to "delayed", the same failure shape a dead daemon thread always had. The code default remains unset (thread); pinamar.humanrounds.org and the demo run `=1` (one container, `worker.py` supervised by `asgi_main.py`), and the value on salud.pinamar.gob.ar is not visible to us (2026-10-28). Tests: `tests/test_queue_worker.py` (delegation matrix, supervisor, real-subprocess lifecycle, stopped-worker durability, two-worker single-execution, periodic-tick uniqueness).
- **Cancel + waitlist (2026-07-16): `lista_espera.py` (engine + sweep) is NO LONGER isolated.** The trigger is a "Cancelar" link for the patient (a discreet link, not a button — ui-rules), with confirmation on the SAME screen, in `/my-requests` (`renderAcciones` panel, below the table — the table itself carries no inline controls) and in `/request/<id>`; both reuse `window.SanaRequests.cancelUi` (my-requests.js). `POST /api/requests/<id>/cancel` (solicitudes.py, owner=dni OR solicitante_dni; cancelable = pending, or approved with a future appointment — past → 400 `turno_pasado`) sets `estado='cancelada'` and, if it freed up a future slot, triggers `lista_espera.liberar_slot` (lazy import, best-effort: the cancellation ALWAYS persists even if the re-offer fails). Opt-in "let me know if an earlier slot opens up" = `POST /api/requests/<id>/waitlist {activo}` (same module; the email ALWAYS comes from the requesting account — no email, 400 `falta_email` with a link to Mi cuenta); UI only on `/request/<id>` (`window.SanaRequests.waitlistUi`) because it's the only surface that knows the real state (`_public_detail` carries `lista_espera_activo`; the list's `_public_row` does NOT, to avoid showing a checkbox that could be lying). The email's link (`lista_espera.notificar_oferta_turno`) points to `GET /appointment/offer/<token>` (`lista_espera_api.py`, a new module — the token IS the auth, same pattern as calendario.py): primary button "Tomar este turno" + secondary link "No lo quiero," resolved client-side by the server bootstrap plus `app/modules/turnos/offer.mjs` against `POST /api/offer/<token>/{accept,reject}` (it never navigates to raw JSON). Accept = `lista_espera.reclamar` + `db_booking.reassign_appointment` (new turno_dt, leaves `estado='aprobada'`) + push to HSI reusing `solicitudes._push_hsi` (persists locally even if HSI fails) + `notificaciones.notificar_aprobada`. Reject = `lista_espera.rechazar_oferta` (new: frees the slot RIGHT AWAY, doesn't wait for the window to expire, and moves on to the next person in the queue). The expiration sweep runs as a daemon thread (`lista_espera.start()`, started in `server.py:main`, same pattern as `recordatorios.py`; `TURNOS_WAITLIST_OFF=1` turns it off, `TURNOS_WAITLIST_INTERVAL_MIN` default 2 min). Admin queue: `admin.html` knows how to paint the `cancelada` chip/cell (gray, "Cancelada por el paciente") — a minimal change, not a redesign. Tests: `tests/test_booking_requests.py` (`TestCancelar`, `TestListaEsperaToggle`, `TestListaEsperaApi`, `TestCarreraListaEspera` — the last one is the full flow: A cancels → offer to B → B accepts).

## WhatsApp to the patient: confirmation and day-before reminder (2026-10-21)

The product owner's decision (q708829): the patient gets a WhatsApp with every detail of
the appointment the moment it is confirmed, and a reminder the day before.

- **When.** The confirmation rides `notify_approved`, so it goes wherever an
  appointment becomes concrete: auto-confirmed at booking, approved from the
  queue, created by the desk, rescheduled, taken from a waitlist offer. A
  pending request with no time gets nothing by WhatsApp (its email says
  "recibimos"). The reminder rides `notify_reminder` (day-before sweep,
  09–21 ART), which answers `sent`, `skipped` (nothing to send: no address
  and no phone, or the channels off) or `failed`; a `skipped` one keeps its
  claim (`reminder_at`) and is marked `reminder_skipped`, so the report
  counts only reminders that went out (2026-11-10). WhatsApp and email are
  independent: no email on the account
  still sends the WhatsApp.
- **What.** Eight values, the same for both, built once by `send._wa_fields`:
  patient, service, when, where (center + address), who sees them
  (`medico_asignado`, else the catalog name behind `medico_asignado_id`),
  what to bring (DNI always, the referral when the appointment has one, the
  preparation's `traer` items, deduplicated), preparation (fasting + the
  `antes` steps) and the link to cancel or change it (`/my-requests`, where
  both actions live). A value is never empty — Meta rejects the template.
- **How.** Hospital-initiated messages are only delivered by Meta outside
  the patient's 24h window as an approved template, so on Meta they go as
  the Utility templates `turnos_confirmacion` / `turnos_recordatorio` (es_AR,
  WABA of the installation; the reminder carries two quick replies
  «Sí, voy» / «No puedo ir», which arrive at the webhook as `type: button`
  and resolve through `confirmations.respond` like a typed SÍ/NO). On WAHA
  (loopback dev) or without a template the same lines go as free text
  (`_wa_text`). One gated entry point: `otp_send.enviar_notificacion`.
- **Gate.** `otp_send.notificacion_permitida`: off unless
  `TURNOS_WA_NOTIFY=1`; `TURNOS_WA_TEST_RECIPIENTS` restricts to those
  phones. Pinamar runs with it off until it has its own number and the
  municipality's consent — and the rejection remedy, which used to go by
  free text whenever a provider was configured, now sits behind the same
  gate. In the demo the list is mandatory and env-only (the public demo
  admin cannot widen it), and with notices + list set the demo also runs
  its reminder sweep (`TURNOS_REMINDERS_OFF` flips to 0; mail stays off).
- Tests: `tests/test_whatsapp_patient_notices.py`, `TestRecordatorioWhatsApp`
  in `tests/test_notifications.py`.
