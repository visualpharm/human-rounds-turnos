- **Editable admin content (2026-07-11): a Postgres overlay on top of the base JSON.** `webdata/*.json` is still the authored base; the `catalogo` table (`tipo,id,doc jsonb,borrado`) stores admin edits and WINS by id: an override overwrites the whole doc, a new id gets added, `borrado=true` hides it (soft-delete of a base id; DB-only ones get hard-deleted), "restore" = delete the row (reverts to the JSON original). `catalogo.py` = merge (3 s TTL cache; DB down → base alone, the site NEVER goes down because of this; `admin_list` is strict instead → 503) + per-type validation — the walk-in invariant is validated here: a `walkin`/`walkin_con_orden` service can NEVER have an `agenda`. `admin_contenido.py` = CRUD `/api/admin/content/<tipo>` (centros|servicios|medicos; GET/POST/PUT/DELETE + `/restaurar`, all behind `admin_auth`). UI: Servicios/Centros/Médicos sections in admin.html + `admin-content.js` (hash-routing `#app/services/<id>`, edited/new/deleted badges, live schedule preview via hours.mjs, `<details>` with the webdata original). The existing doctor editor (`#doctors/<id>`) has THREE tabs — **Horarios de atención first and by default** (2026-07-16: reverses the initial order, which started on Calendario; `data-tab` is still `"agenda"`, only the label changed), Calendario second: approved appointments grouped by day via `GET /api/admin/doctors/<id>/appointments?days=30` (owner `medico_turnos.py`, `solo_admin=True`, same visual language as admin-my-appointments.js; the fetch still fires on entering the editor even though the panel starts hidden), Información básica third; a new doctor (with no id yet) has no Calendario tab and still starts on Horarios de atención. Each center's card is white against the admin's gray background (`.cnt-centro-block`, same language as `.card`), with no divider lines under the tabs or between hours/exceptions (the whitespace already separates them); "Eliminar" is a gray button (`.btn-quiet`, no longer a red link) on the same row as Guardar, right-aligned next to "Restaurar original" (`.cnt-actions`/`.cnt-actions-danger`). The admin's `#doctors` listing is a MANAGEMENT view, not the public site's: `GET /api/admin/doctors/stats` (owner `medico_turnos.py`, `solo_admin=True`) computes per-doctor hours/week, next day, occupancy/appointments in 14 days, whether they have a photo/login, and number of services (a single query against `listar_aprobadas_futuras` grouped in Python, not N+1); `admin-content.js` requests it in parallel with the base listing and merges by id — if stats fails, the base table still shows. Configurable columns via a gear icon in the toolbar (persisted in localStorage `st_adm_med_cols`) + `<select>` filters for Centro/Especialidad/Agenda (never pills) that compose with the search box. Real weekly schedules: `agenda` field `{dias,desde,hasta,cada_min}` on the doctor (and on bookable services) — same shape as `agenda_demo`; preference in `_medico_proximo`: real agenda > agenda_demo > MSD. WATCH OUT: `dias` uses the JS convention `Date.getDay()` (0=Sunday..6=Saturday, same as hours.mjs/week.js); Python matches with `isoweekday() % 7` (`hospital._demo_proximo`). Appointments and patient data still live in HSI — our DB holds only site content and availability.
- **The engine is generic; the locality's data is a swappable package (2026-07-16).** `datos.py` is the SOLE owner of where the data package lives: `TURNOS_WEBDATA_DIR` points to another directory (e.g. `webdata-ejemplo/`, the fictional "Sampleton" town that covers all 4 modes), without the env var it's `webdata/` (Pinamar). NEVER build `os.path.join(..., "webdata", ...)` by hand in new code — always `datos.path(fname)`. In tests, the fixture seam is `os.environ["TURNOS_WEBDATA_DIR"]` + clearing `catalogo._JSON_CACHE`/`hospital._CACHE` (patching `catalogo._DIR` no longer does anything — that's how 31 tests broke in the split). **Phase 2 (same day): `sitio.py` owns the site's IDENTITY** (locality, hospital name, emergency "107") — it lives in `sitio.json` inside each data package (`datos.path("sitio.json")`, same mtime-cache pattern as `hospital._load`; missing file → neutral defaults, never a crash). Two consumption styles: Python code (hospital.py, cuentas.py, preparacion.py, calendario.py) calls `sitio.get("clave")` directly, immediate substitution; server-rendered static pages (`index.html`, `about.html`, `privacy.html`, `terms.html`, served by `sitio.handle()` in server.py's chain) carry literal `{{sitio.clave}}` placeholders that `sitio.render()` resolves (HTML-escaped) only when serving. The footer now has one owner, `templates/_site_footer.html`: `index.html` includes it directly and `site_shell._site_footer()` renders it for every dynamic shell while preserving the legacy newline boundary. Deliberately left untouched: comments/docstrings narrating where Pinamar's current dataset came from, and the 2026-07-08 editorial entry in `_NOVEDADES` (frozen history of THIS deployment, not the engine's copy). Tests: `tests/test_site_identity.py`. The package contract is documented in the README's "Use it in your municipality."
- **Data = `webdata/centros-salud.json` (10 centers) + `webdata/servicios.json` (134 services) + `webdata/medicos.json` (99 professionals)**. 2026-07-08 base authored from https://pinamar.gob.ar/salud/; on 2026-07-12 the Secretaría de Salud's OFFICIAL SPREADSHEET arrived ("Detalle de turnos 12-07-26.xlsx" from reference-deployment counterpart, snapshot in `webdata/fuentes/detalle-turnos-2026-07-12.xlsx`) with 145 real services: professionals, offices, weekly schedules, age groups, keywords, and referral rules. **The "complete" version arrived on 2026-07-14** ("Detalle de turnos completo 14-7-26.xlsx," snapshot `webdata/fuentes/detalle-turnos-completo-2026-07-14.xlsx`) — **2 sheets; Hoja2 is the final, curated one** (Hoja1 is the draft with renamed services: "Consultorio Medicina General" → "Medicina General," workshops moved to the venue "Centro Cultural de Ostende," the "Desarrollo Infantil" program moved to caps-ostende as its venue). Each service: `modo` ∈ `walkin` (signage, no appointment) | `walkin_con_orden` (medical order, first-come-first-served) | `solicitud` (scheduled appointment WITHOUT an order: wizard starts at "Elegí un turno" — mode:"turno" in service.js, POST /api/requests with no orden_token) | `solicitud_con_orden` (upload the order → admin queue), `horario`, `cartel` (signage IS the differentiator vs. Mi Salud Bonaerense), `edad {min,max}`, PAMI note, `consultorio`, and in solicitud* modes a real `agenda` (single-window or `{franjas}` — catalogo.py validates both; the admin editor only edits single-window). `_proximo_turno_best`: MSD > the service's own schedule > its doctors' schedule (cluster+center).
- **Walk-in NEVER offers appointments — on any surface** (the product owner, 2×: wizard 2026-07-09, doctor page 2026-07-10). If the service is `walkin`/`walkin_con_orden`, neither the wizard, nor the doctor page, nor the listings show an MSD schedule slot or a "Sacar turno" button (it would contradict the "No necesitás turno" signage). Server: `_medico_proximo`/`_servicio_proximo` short-circuit to `_con_horario`; `estado()` returns `hasta` (closing time of the current stretch).

- **A center's HSI institution (2026-10-27)**: optional `hsi_institution` (digits, the number in HSI's `…/institucion/<n>/…` addresses), edited in the panel's «Centros» as «Institución en HSI». ### Institutional portraits (slice 5, 2026-10-14)

Doctor uploads are decoded and processed locally with Pillow: EXIF transpose,
explicit 90-degree rotation, mild exposure/contrast/sharpening, center-top square
framing and a 512px WebP. `TURNOS_PHOTO_AUTO_ENHANCE` defaults to 1 and is a
Settings checkbox. Disabled enhancement still creates the correctly oriented,
resized portrait. Original bytes are retained privately with the portrait and
status in atomic version bundles under `data/medico-fotos/.originals/`. A public
symlink serves only each full-size processed portrait; `avatar_sprite.py` still
owns every small avatar. Old uploads can be adopted and processed without
losing original bytes. Restore/reprocess use the same upload endpoint; removal
also removes that doctor's private bundles. Centers retain their existing
upload behavior. A doctor or center deleted for good (nothing names it, so the
row goes rather than being disabled) loses its photos first —
`doctor_photos.erase`: the public file and the whole `.originals/<id>/`, under
the portrait lock; a photo that cannot be removed refuses the deletion (507) and
the record stays. Ids are derived from names, so a photo left behind would show
on the next record with the same name. A disabled record keeps its photos. No external image editing or AI provider is involved.

### Ids the database keeps about catalog entries (schema review №10, 2026-10-24)

Doctors, services and centers are JSON documents (pack + the panel overlay), so no foreign key can protect the ids other tables store about them — checks do, at the two moments an id can go wrong:

- **At the write point.** `POST /api/requests` (`booking_create._check_catalog_refs`) refuses, before anything is stored: a service the catalog does not list, a center that is not a live catalog center or is not the service's own, and a `slot_medico_id` that is not a live catalog doctor in the service's pool (`_doctor_pool`, the rule the desk's approval uses; a demo doctor only has to exist, a lab takes no doctor). A catalog that cannot be read is a `503 catalogo_no_disponible`, never «accept anything» — but only for the part of the catalog the booking names (no center, no center list needed; an unreadable doctor list is a retry, never «that doctor is gone»). The wizard answers a slot doctor refusal by going back to «Horario» with the server's phrase, the rest of the form kept (as for `turno_tomado`). The desk approval always sends the service it shows: with the catalog unreadable the request's own service still approves as before, and only a «Derivar a» another service gets the retry phrase (503); a readable catalog checks it with `_service_valid`. The desk's «Crear turno» already takes center and service from the catalog record and checks the doctor against the pool.
- **When a pack changes.** The panel never renames an id, a pack update can. `python3 scripts/auditar_referencias_catalogo.py [--json]` (read only; `app/patient_web/catalog_refs.py`) lists every id stored in the columns of `catalog_refs.REFERENCES` that the catalog has never heard of (a DISABLED entry still counts as present), with table, column and row count — no patient data. Exit 0 clean, 1 broken references, 2 could not read. Run it before publishing a pack that renames or drops an id, and after. `test_catalog_refs.TestRegistryIsComplete` fails when a new column holding such an id is missing from the registry. There are no separate doctor/service tables: the checks are the design.
