# Listings, columns, search, nav, UI

Extracted from CLAUDE.md 2026-07-29 (verbatim). These are load-bearing decisions — **do not relitigate** what is marked as such. Read this file before touching the code it describes.

- **Canonical column registry: `static/platform/listing.mjs` is the single source of truth for ALL tables on the patient site.** `PRESETS`/`COL_ORDER` in `listing.mjs` (mirrored in `hospital.py:_COL_PRESETS`/`_COL_ORDER`/`_cols(...claves)`) defines type/data/href/label/order per key; a page passes keys or `{preset,...override}` and listing.js ALWAYS reorders them into the **entity-first canonical order**: entity (`servicio`/`estudio`/`medico`) · context (`especialidad`/`area`) · `centro`/`lugar` · `estado` · `orden` · `proximo`. **The `turno` column ("Sacar turno") DIED (the product owner, 2026-07-12): the Próxima disponibilidad pill IS the button, and since the 2026-07-14 mockup it states the VERB** — bookable with a known date → `<a class="lst-time lst-time--{ya|semana|lejos}" href>` "Sacar mañana, 13:00" / "Sacar el martes 21 de julio, 13:00" (sage green from the design system `--ok #6f9959` darkened to `#567b42` for AA contrast against white text; amber/taupe for the farther-out tiers) + bold link "Más horarios" to `info_href` (the service page, which shows the weekly grid; suppressed if `info_href === href`); bookable with NO known date → TINTA-colored "Sacar turno" button (`lst-time--pedir`) + a plain-text note "La fecha la confirma el centro" (the note is information, never button chrome); walk-in → plain GREEN text with NO box (`.lst-open`) + gray suffix "por orden de llegada." The Orden cell is no longer a pill (ui-rules 2026-07-14: pill only if it MUST be a pill): "Con orden" = ink-colored text + an ⓘ icon that opens an explanatory popover, "Sin orden" = plain, dimmed text. A shown appointment is ALWAYS the first available one, never the only one: hence "más horarios." The `orden` column (Con orden/Sin orden) appears in EVERY table, including doctors' (`_medico_orden`: `None` when it can't be known → empty cell, never a false "Sin orden"), and it's the only one hidden on mobile (`hideSm`) — the appointment column never leaves the screen. Every centro/especialidad cell links to its page (`centro_href`/`esp_href`). One line per cell (`white-space:nowrap`) on desktop. **Responsive (the product owner, 2026-07-15 — reverses the "full-bleed horizontal scroll" from 2026-07-12): below 1040px the table does NOT fit as a table** (the appointment button with the full date measures ~230px and combined with servicio+centro+orden it overflows; the horizontal scroll used to hide precisely the appointment column, which IS the control). That's why `@media(max-width:1040px)` in `listing.js` STACKS the row (the product owner, 2026-07-15, refined against study photos): **servicio/estudio** = entity **+** `centro`/`lugar` on the SAME line separated by ` · ` (`td.lst-td-link` inline + `td.lst-td-sub` inline-block nowrap with a `::before` middot; the center drops ENTIRELY to line 2 ONLY if it doesn't fit) and the appointment button below with little breathing room (`.lst-td-proximo{margin-top:6px}`, previously 11); **doctor** (row `.lst-row-av`, marked when any column carries `avatar`) = avatar + name on line 1 and the button (and the center if present) aligned BELOW the name, not the avatar (`padding-left:56px` = avatar 44 + gap 12). Columns marked `hideSm` get hidden; **"Más horarios" also stays stacked** (the product owner, 2026-07-16: hiding it was a bug — the button with `?slot=` skips the grid, so without the link a phone had no visible path to the other times; reverses the "redundant" call from 2026-07-15). Listing-page shell width went up to **1120px** (index.html, hospital.py, cuentas.py — the prose/legacy ones stay at 1000) so the button + "Más horarios" don't get clipped on desktop. ALWAYS verify in-browser at 360/390/834/1041/1280 with the `responsive` skill's overflow-probe (zero horizontal overflow; the 1040↔1041 stack↔table boundary is the critical point). **Single-choice filters are `<select>`, NEVER pills** (the product owner, 2026-07-15 + ui-rules 2026-07-14): `t:"facet"` (Área) and `t:"publico"` (Para) render as a dropdown whose default value IS the field's label ("Área"/"Para"), not a generic "Todos"; only `t:"sexo"` (binary toggle) stays a checkbox. Tests: `tests/test_listado_consistencia.py` + `tests/listing-order.test.mjs`.
- **Order and color of "when":** in the sort by next availability, tier "0" is EXCLUSIVE to bookable appointments — "with an appointment" ALWAYS comes before any walk-in, even one open right now. Walk-in = tier "1" (open → opening by date → generic ones), "2" = the center confirms the date (`listing.js:ORDEN`). Proximity color ONLY applies to bookable ones, and since 2026-10-19 (the reference-deployment counterpart's call) EVERY slot is green — no amber, no gray, never red: the wait only shifts the same green toward a blue in 11 steps of 3 days (`ORDEN.bucket` → `w0`…`w10`, mirrored by `site_studies._cta_bucket`, CSS `.lst-time--wN` / `.mp-cta--wN`; `tests/test_slot_green.py`, `tests/listing-order.test.mjs`). A «con orden» row's action is **«Subí tu orden»** (`orderPill`, band button too) with the first appointment as a note; a bookable row with NO open turnos shows the plain message «No hay turnos disponibles» with «Se habilitan a partir de: …» on the line below, both free to wrap (`habilitaCell`, since 2026-11-13 — a one-line `nowrap` cell took the table's spare width; server field `proximo.habilita` from `site_availability._habilita`/`_next_opening`) and never a «Sacar turno» button. **Walk-in is no longer the muted variant** (reverses the 2026-07-11 rule): it's green text, with the same visual weight as an appointment, because it's also a legitimate way to get seen — what changes is the FORM (button = you book; text = it opens and you go), not the hierarchy.
- **Ranking by weekly attendance hours in both search AND listing pages (the product owner, 2026-07-12/14).** `search.js` (`SanaSearch.ordenarPorPopularidad`) groups by normalized name, sorts groups by TOTAL hours desc and each group's rows by hours desc. **Entry points: `opts.rank:"popularidad"` in listing.js for catalogs WITHOUT a query; the home search uses `SanaSearch.buscar` (below) and passes `defaultSort:false`** — listing.js leaves the default sort as "none" (headers still re-sort on click: the list starts by popularity, the user can switch to next availability). The hours come from `hospital._horas_semana` (the service's own schedule > sum of its doctors' time slots in the same cluster+center > 0) and live on each row as `horas`. Popularity proxy: we don't have appointment statistics, but we do know how many hours a service is attended. **They rank ENTITY CATALOGS**: home (services+doctors), services of `/center/<slug>`, `/estudios`. **Doctors' lists are NOT ranked (demo review 2026-11-15, P20):** `/doctors`, the doctors of `/d/<cluster>` and of `/center/<slug>` read soonest availability first, then name (`site_listing._soonest_first`, no `rank`). **They do NOT rank the "pick the center that sees you sooner" surfaces** (`estudio-centros`, `cluster-centros`): there, a single study/specialty lives across several centers and next availability rules (patient-flow rule 7 — wait + travel), not popularity. Acceptance case: "medicina gene" → plain "Medicina general" first (89 h across 3 centers). Tests: `tests/search-order.test.mjs` + `TestRankingPopularidad` in `tests/test_listado_consistencia.py`.
- **Every search/filter is its own shareable URL (the product owner, 2026-07-17).** The home (`index.html:syncUrl`) syncs the `#q` search box with `?q=` (`history.replaceState` — the address bar always mirrors what's shown, without cluttering history keystroke by keystroke; on load it already reads `?q=`). In `listing.js` it's **opt-in via `opts.urlState:true`**: on mount it reads `?q=` (facets were already read) and REWRITES `?q=` + the facet keys as you type/filter (`writeUrl`, preserves other params and the hash). Opt-in on purpose: on pages with TWO listings (`/center/<slug>`) both would write the same `?q=` and clobber each other, so it's only enabled where there's ONE searchable listing — `/doctors` (`medicos-tabla`) and `/d/diagnostico`=Estudios (`estudios-tabla`; its `cluster-medicos` has 0 rows and doesn't mount). Verified on `:7700`: typing/choosing a facet updates the URL, and opening `/doctors?q=cardio&specialty=Cardiólogo` cold restores the box+select+filtering. It does NOT sync column sort (the product owner didn't ask for it) nor `publico`/`sexo` (those come from the profile). `listing.js` is content-hash fingerprinted (`static_fingerprint.CLIENT_LOADED` — pages reference `static('listing.js')`/`url("listing.js")`, and `lab-results.js` loads it at runtime through `window.SANA_STATIC`); there is nothing to bump when touching it.
- **Home search = `SanaSearch.buscar` — stemming + relevance tiers (2026-07-16, do not relitigate).** The search study found that "ginecólogo"/"cardiólogo"/"obstetra" returned ZERO results (people search for the professional, the catalog names the specialty) and that "gine" showed Medicina general 6× (a synonym with lots of hours) before Ginecología. `search.js:buscar(rows, q, getCampos)`: each query word generates morphological variants in BOTH directions (-ólogo↔-ología with a minimum 2-char prefix [urólogo], -iatra↔-iatría, -grafía↔-grafista, -ico↔-ica [médico clínico→Clínica Médica], plural→singular, irregulars obstetra/diabetes/médico/enfermería) and is scored by tiers: name-STARTS-WITH (0) > start of another word in the name (1) > substring of the name (2) > start within the rest/synonyms (3) > substring of the rest (4); AND between words, score = sum, and hours only sort WITHIN each score — relevance rules, popularity is the tiebreaker. Stopwords include dr/dra/lic; the process's meta-words (turno/sacar/pedir/cita/consulta) are ignored only if the query says something more. Fields: `principal:[nombre]`, `resto:[categoria, centro, sede, horario, palabras]` (doctors: `[especialidad, centro, palabras]` — matches both "Cardiología" AND "Cardiólogo," the noun from `_esp_medico`). Role-rows from the spreadsheet ("Enfermería," "Técnico/a," "Administrativo.") carry `rol:true` in medicos.json and `hospital._profesionales()` filters them out of the directory/search/center/cluster views WITHOUT removing them from `_horas_semana`/`_turnos_servicio`. Detail + gotchas (orphaned server on :7700, stale duplicates from the import): `docs/solutions/design/busqueda-stemming-tiers.md`. Tests: `tests/search-match.test.mjs`.
- **Home search also leads to informational LINK pages, not only consultorios (2026-08-27 hospital meeting).** `packs/<pack>/enlaces.json` (`catalog.py:links()`/`link_by_id()`, `site_centers._links()`/`_link_by_id()`, pack field `enlaces` — same override-pack + admin-overlay contract as `centros`/`servicios`) lists informational destinations (telemedicina, zoonosis, donar sangre today) that are NOT a consultorio: each has an `id`, `nombre`, `descripcion`, `href` (an internal page, e.g. `/telemedicine`), a `palabras` search-keyword list, an optional `palabras_excluidas`, and a `pagina` object the page itself renders from (see `site_news._page_telemedicine`/`_page_zoonosis`/`_page_blood_donation`). Served at `/api/links` and searched with the SAME engine as everything else — `index.html:campoEnlace` feeds `SanaSearch.buscar(ENLACES, q, campoEnlace)`, no engine fork. They render in their OWN canonical `listing.js` table ABOVE services/médicos, deliberately NOT interleaved score-by-score — a symptom query ("fiebre") always shows Telemedicina first without having to out-tier every service whose `palabras` happens to also mention it. The information row carries service, description and a right-aligned `accion` preset; its button names the destination and never implies that it books a clinical appointment. **An excluded PHRASE hides a row only when the query says the whole phrase** (2026-10-19): a single-word exclusion keeps its two-way prefix rule, but the guardia phrases on Telemedicina («fiebre con confusión», «tose sangre») used to hide it for «fiebre»/«tos» alone; `search.mjs:fraseExcluida` and `app/core/search_exclusions.py` (remedies, chat) share the rule. `pack_l10n.FIELDS["enlaces"]` translates all patient-visible campaign prose, including list fields. `packs/<pack>/announcements.json` can attach an active notice to exact `service_ids`, whole `cluster_ids`, or informational `link_ids`; service and campaign pages render these immediately below their title, while inactive records remain drafts. Post-booking, `service.js`'s success screen adds one discreet text line pointing at `/blood-donation` (`.wz-donate-note`, `service.success.donate_note`) — never a banner.
