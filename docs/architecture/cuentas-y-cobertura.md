Extracted from CLAUDE.md 2026-07-29 (verbatim). These are load-bearing decisions — **do not relitigate** what is marked as such. Read this file before touching the code it describes.

- **Patient accounts from the municipal portal (2026-10-23, product owner 21.10).** With `TURNOS_PATIENT_PORTAL_LOGIN=1` (installation env only; needs `TURNOS_PORTAL_IDENTITY_MODE=private-gateway-v1`, or `test-portal-v1` for the in-process test portal of pinamar.humanrounds.org (`app/cuentas/test_portal.py`, 2026-10-25); the process refuses to start otherwise) the portal is the patients' only way in. `accounts.current_user` finds the account by `users.portal_user_id` (`X-User-Id`, partial unique index, Alembic `0025_patient_portal_user_id`); on the first request `db_accounts.user_claim_portal` binds the account with the DNI inside the validated CUIT (`portal_identity.person_dni`: the eight middle digits without leading zeros) or creates it active with no password and the portal email. Refused, nothing written: an organization's CUIT (anything but 20/23/24/25/26/27), a disabled account, an account already bound to another portal account, a bound account whose DNI no longer matches the CUIT. Without the flag the reviewed-binding pilot keeps its old rule exactly (no person-CUIT check). The portal email fills an empty email only. The name the portal asserts (`portal_identity.assertion_name`: `X-User-Given-Name`/`X-User-Family-Name`, or `X-User-Name` as «APELLIDO, Nombre») fills EMPTY name fields at creation and on any later request (`db_accounts.user_fill_name`) — never overwrites a saved name (2026-10-30; before it, every portal account was born nameless and showed «—» in Pacientes). A portal account still without a name keeps opening on «Mis turnos»; Confirmá asks for it when the account has none and saves it with the contact. The phone is not sent by the portal. `TURNOS_PORTAL_IDENTITY_BINDINGS` stays as a pilot limiter (a list admits only its subjects; empty admits everyone). `auth_mode` is `portal`: every `renderAuth` surface shows «Ingresar con el portal» (`TURNOS_PORTAL_LOGIN_URL`) instead of the forms — or, when the gateway vouched for the person but no account opened, the help-line remedy; nav has no «Registrarse» and no «Cerrar sesión»; `/api/account/{login,register,recover,reset,reset_otp,test-login}` answer 403 with the portal URL and `/account/reset` redirects to `/account`. DNI-photo sign-up stays the default for every other installation. Proofs: `tests/test_patient_portal.py`. Contract: [portal-gateway-identity.md](../portal-gateway-identity.md).

- **Unified patient coverage picker (2026-10-21).** Registration and account editing share one searchable **Obra social o prepaga** control in `static/platform/account-form.mjs`; this supersedes the separate OS/prepaga UI described historically below. Both existing catalogs are searched together, ignoring case, accents, spaces and punctuation. Catalog choices keep their original category and name; loaded legacy/registry values keep their name, category and RNOS. Unknown names require an explicit manual choice of category. A typed query is never a saved insurer; Escape/blur restores the selected value. The small right-side remove button appears only for a selected value and restores focus to the nearest remaining picker after removal. Member fields, prepaid plan, multiple coverage and the existing server contract remain: up to six `obras_sociales` plus one `prepaga`. Duplicate/over-limit choices are disabled rather than silently dropping/reclassifying a value. The server still owns registry origin and principal selection. `leerCobertura` always includes `obras_sociales: []` for editor deletion, while unrelated visitor flows omit coverage. Delayed registry responses preserve an active search and selected private plan; returning to registration does not recreate removed registry rows. Browser evidence: `tests/account-coverage-browser.test.mjs`, with all requests mocked and no database/provider access. ES/EN copy is authored; other locales use the canonical fallback pending the existing translation pipeline.

- **Registration transaction (2026-10-21):** the native `POST /api/account/register` calls `accounts_store.create_user_and_session`. The account and its first session commit in one transaction; a session INSERT failure rolls both back. It returns the inserted public user, avoiding a separate post-commit lookup before setting the cookie. `ON CONFLICT (dni) DO NOTHING` maps only a DNI collision to the existing 409 without changing the old password/contact, independently of legacy constraint names. Synthetic key collisions redraw within a bounded three-attempt loop. For email-bearing registrations, a transaction advisory lock serializes the existing no-DNI email check; DNI accounts may still share a family email. This is registration-only coordination, not a global email uniqueness rule: profile edits and provider account writers retain their existing behavior. A lost HTTP response after commit can still require login/recovery; the existing phone-verification ticket consumption is unchanged. Recovery still uses the stored contact and generic response; this slice introduces no contact-verification or recovery policy. Regressions: `tests/test_registration_atomic.py` (native HTTP, actual application composition, synthetic per-run Postgres).

- **Health coverage/prepaid plan at registration (2026-07-16, multi-coverage from day one): `puco.py` + `usuarios.cobertura`.** The registration form fires `POST /api/puco {dni}` as soon as the DNI is complete (600 ms debounce, runs IN THE BACKGROUND while the person fills in the rest) and shows ALL the health coverages registered under their name in the national registry — a person can appear in more than one registry (IOMA + a deregulated prepaid plan) and can also declare others by hand via the "Agregar otra obra social" link (SISA PUCO, WS131 REST: `POST sisa.msal.gov.ar/sisa/services/rest/puco/<dni>` with `{"usuario","clave"}`, XML response; the parser picks up ALL the `coberturaSocial` entries that come back; WATCH OUT `denominacion` = the CITIZEN's name, not the coverage — NEVER re-exposed to the client). Response: `{"disponible": true, "obras_sociales": [...]}` (+ `obra_social` = the first one, for compat with cached old JS). Hit → each registry coverage is NON-editable TEXT + a green note ("Figura/Figuran a tu nombre en el padrón nacional.", shown once); miss/PUCO down → manual combobox; next to it, always, the "Prepaga (si tenés)" field. The coverages section is a LIST of rows (`osSectionHtml`/`wireOsSection`/`leerObras` in account-form.js, items in `host._osItems`; in renderAuth `paintOsSec` repaints while preserving items — "Agregar otra" — and `renderOsSec` only rebuilds the model on PUCO state changes: rebuilding would filter out a just-added empty row). Manual inputs are **comboboxes** (`comboHtml`/`wireCombo`: focus → full list, typing → accent-insensitive filter, arrows+Enter, free text ALWAYS valid — the list suggests, it doesn't restrict). The lists (`OBRAS_SOCIALES`/`PREPAGAS`) come from frequency in Pinamar's private cartilla (`<workspace>/salud-pinamar/cartilla-2026-05-14.json`: OSDE 129, IOMA 90, Federada 63…) with PAMI bumped up manually (the private cartilla underrepresents it, but it's THE public one for the municipal hospital). Env `TURNOS_SISA_USER`/`TURNOS_SISA_PASS` (**pending: SISA account with WS131 — requested from the reference-deployment counterpart 2026-07-16**). **Source order in `consultar()`: fake → WS131 REST (if creds exist) → public GWT-RPC lookup → manual.** Without creds it does NOT fall back to manual: it uses the public fallback `_consultar_publico` (SISA's public "Consulta de Cobertura de Salud," two `text/x-gwt-rpc` POSTs with no credentials — `LoadEnvironmentAction` mints the `JSESSIONID` → `ListService.getPage`; `_parse_publico` picks up ONLY the Cobertura from each row, the Denominación=NAME never comes out; session cached 4 min + retry). Env `TURNOS_PUCO_PUBLIC` (ON by default, `0` turns it off) and `TURNOS_PUCO_GWT_PERM_DISP`/`_LIST` (override the GWT strong-names with no redeploy if SISA redeploys). Deliberately fragile: expired hash → `//EX` → `ok=False` → manual, never a false "not found." **Verified in prod 2026-07-16 from Coolify's datacenter IP (no reCAPTCHA wall).** Recipe and caveats: `docs/solutions/sisa-puco-gwt-rpc-api.md`. `TURNOS_FAKE_PUCO=1` = no network (DNI's last digit 0-3 → IOMA, 4-5 → IOMA+OSECAC [the multi case], 6-7 → OSECAC, 8-9 → not found). Own rate limit 30/h per IP (`TURNOS_PUCO_PER_HOUR`) — a bucket separate from abuso.py so it doesn't eat into the same IP's AI quota. `usuarios.cobertura` jsonb = `{obras_sociales: [{nombre, rnos?, origen: "puco"|"declarada", afiliado?}, ...], prepaga: {nombre, afiliado?, plan?}}` (tolerates the singular `obra_social` saved before 2026-07-16 and the bare prepaid-plan string): coverages with origin `puco` are attached ENTIRELY SERVER-SIDE from the active insurance_lookup connector's cache — `app/cuentas/accounts.py:_norm_coverage` resolves it as `connectors.adapter_for("insurance_lookup").cached(dni)` (registry rewire 2026-08-20; puco is the flagged default, its `cached()` is `puco.cacheada()`'s 15-min TTL cache; `conn disable insurance_lookup` → `[]` → everything the form sends is `declarada`, nothing breaks; the client can't invent a coverage "according to the registry") but the **member/affiliate number and plan always come from the body, per coverage** (the registry doesn't carry them, only the patient knows — rows revealed only when that coverage has a value: OS → "Nº de afiliado," prepaid → "Nº de socio" + "Plan"); `_actualizar` without the `cobertura` key keeps what's saved, and sending `obras_sociales: []` while mentioning the key is a deliberate wipe (that's why renderEditar ALWAYS includes the key). Tests: `tests/test_puco.py`.

- **Cobertura: una es la principal (2026-07-24, responsable del producto).** `cobertura.py` decide cuál de las coberturas de una persona manda: lo marcado a mano gana SIEMPRE, y si no hay nada marcado propone la mejor — una prepaga le gana a cualquier obra social (el caso que planteó el responsable del producto: dos obras sociales y Swiss Medical → Swiss Medical) y entre prepagas ordena la satisfacción medida 2026 (Swiss 3,85 · OSDE 3,73 · Federada 3,70 · Medicus 3,6x); PAMI/IOMA van último ENTRE obras sociales porque cuando hay además otra, esa conviene — quien sólo tiene PAMI la ve como principal igual. WATCH OUT: los nombres del padrón vienen como `O.S.P. BUENOS AIRES (I.O.M.A.)`, así que `_norm` saca puntos Y el matcheo prueba también sin espacios; sin eso IOMA empataba con todas y ganaba por orden de carga. Tests: `tests/test_health_coverage.py`.

- **A DNI change moves the whole clinical identity (formal sweep 2026-09-24, Lean `DniMove.lean`).** `db_accounts.change_dni` is driven by three registries next to it: `DNI_MOVED_COLUMNS` (every column holding this person's DNI, clinical tables included), `DNI_PREFIXED_KEY_COLUMNS` (chat keys `dni:<dni>[:…]`, including the WhatsApp handoff grant) and `DNI_KEPT_COLUMNS`, each with its reason: `dependents.dni` (a dependent is another person declared by another account — only this account's `adult_dni` link moves) and `hsi_patients.dni` (HSI's own mirror). `test_formal_invariants.TestChangeDniClosure` enumerates the live schema and fails when a new DNI column is in neither list. - **The signed-in patient in a route is a dependency (2026-11-11, `app/cuentas/account_deps.py`).** A route that needs the account declares `usuario: dict = Depends(account_deps.current_account)` (401 `{"error": "no_autenticado"}` without one) or `Depends(account_deps.optional_account)` (None); both are `accounts.current_user(request)` off the event loop, read once per request. A dependency runs before the route body, and on a portal installation reading the session can create or bind the account, so a route that reads the session only after another step (the `?lang=` switch of a page, the body-size check of a chat turn, the 404 of the lab link with no key, FastAPI's 422 of the lab upload and delete) keeps its own read — `tests/test_account_deps.py` holds that inventory. Neither dependency for a route with a typed parameter or a declared body: those are validated after the dependencies.
