# i18n (multi-language)

Phase 3a of the open-source rework (`~/.claude/plans/large-rewrok-before-open-robust-chipmunk.md`), 2026-07-30, built the CORE slice: the resolution engine, the switching modes, the translation cache — proven on ONE page (`about.html`) and ONE data surface (preparation summaries).

**2026-08-04 turned it on for the whole patient site.** The demo had been running with English chrome over a Spanish site: every specialty, service, cluster title and center description stayed in Spanish, and the language switcher disappeared the moment a visitor left the home page (the product owner: "we don't translate any content… the demo header isn't consistent across the site"). Four things closed that:

1. **The language is resolved once per request** (`i18n.bind()` in `routing.dispatch()`, read anywhere via `i18n.active()`) — see "Request-scoped language" below. `site_shell._shell()` was hardcoded `<html lang="es">` with the demo bar's switcher off, because it never sees a handler; now every page it builds carries the real language and the switcher.
2. **Pack CONTENT is translated at the loader boundary** — `pack_l10n.py`, below.
3. **The catalog ships inline on non-canonical pages**, which unblocked JS literals — see "Why JS literals were untouched (fixed)".
4. **A daemon fills the translation cache** (`translate_warmup.py`) so no page render ever waits on a model call.

## Why two modules

- **`i18n.py`** — UI STRINGS. Short, curated, hand-translated (a person writes the English for "Confirmá tu turno"). Canonical language is Spanish (`locales/es.json`) because the product itself is Spanish-first — this is the mirror image of `prompts.py`'s English-canonical choice, made for the same reason in each direction: canonical = whatever a human actually authors first.
- **`translate.py`** — PACK CONTENT. Long-tail, data-driven, MACHINE-translated with caching (a service name, a preparation summary, a center description — hundreds of entries, no person is going to hand-translate all of them into every enabled language). Canonical language is whatever the active pack's `pack.json` says (`language: "es-AR"` for Pinamar).

Both reuse the shape `prompts.py` pioneered (canonical text + a translated/edited counterpart, `TURNOS_FAKE_AI` honored, OpenRouter via `config.get("TURNOS_AI_MODEL")`), but neither imports `prompts.py` — same reason `prompts.py` itself gives for not importing `ai_referral`/`chat_agent`: avoiding an import cycle, and the three modules solve genuinely different problems (paragraph-aligned 3-way merge for an edited *document* vs a flat key/value UI catalog vs a hash-cached data field).

## `i18n.py` — UI strings

### Key naming

Flat, dotted-string keys in a single-level JSON object — **not** nested JSON trees:

```json
{
  "about.hero.intro": "Acerca de",
  "about.section1.item_services_label": "Servicios y estudios:"
}
```

Chosen over nesting because `i18n.t(key, lang)` does one dict lookup by the literal dotted string; nesting would need a walk (like `site_identity.get()`'s dotted-path walk over `sitio.json`) for zero benefit — nobody hand-edits `locales/*.json` by opening the nested tree, they grep for the key. Namespace by page/feature (`about.*`, and — once the extraction fan-out starts — `booking.confirm.*`, `admin.queue.*`, etc.).

`_comment` is a reserved key in both catalog files (repo convention, not enforced by code) for a one-line note on the file's status — never looked up by `t()`, safe to leave untranslated.

### Canonical public Jinja pages

The four public identity pages (`index.html`, `about.html`, `privacy.html`, and `terms.html`) live only under `templates/`. Dark and native transports both call `site_identity.render_page()`, which renders those canonical files through the shared Jinja environment. Root-level HTML copies and the separate regex implementation have been retired.

**Order still matters inside returned fragments.** A translated catalog string or legal body may embed `{{sitio.city}}`. The Jinja `t()` and `legal_doc()` globals resolve that nested identity token after translation/legal lookup and before returning the fragment. This preserves the former two-pass result without rescanning the completed HTML. `i18n.inject_html_lang()` and `i18n.inject_bootstrap()` then apply the request language and client bootstrap, followed by theme and demo-banner injection.

Other legacy fragments may still carry `{{t.*}}` and use `i18n.render()` directly. That compatibility mechanism is separate from the four converged public-page sources.

### Resolution order

`i18n.resolve_lang(handler)` (handler optional — `None` resolves as if there were no request context, e.g. for a cached/edge render):

1. **`lang` cookie**, if it names a currently ENABLED language (`config.get("LANGUAGES")`, comma-separated, filtered to languages that actually have a `locales/<code>.json` file — a typo degrades instead of producing an unreachable language).
2. **The admin-configured default** (`config.get("LANG_DEFAULT")`), but **only if explicitly set** — `i18n._configured_default()` distinguishes "admin chose es" from "nobody chose anything." An explicit choice outranks a browser guess.
3. **`Accept-Language`**, breaking the tie **only when nothing above decided** (no cookie, no explicit admin default) — the first preference (by primary subtag, e.g. `en-US` → `en`) that's in the enabled set.
4. **The first enabled language** (normally `"es"`, since `LANGUAGES` defaults to just `"es"`).

With `LANGUAGES` unset (the default): `enabled_languages() == ["es"]` always, so step 1 can never produce anything but `"es"` regardless of what a cookie or Accept-Language header says — **this is the invariant the golden-page byte-identity tests lean on**. i18n is a true no-op until an admin opts in, by construction, not by a separate feature flag.

`<html lang>` is set from the request-scoped language on the public templates and the shared patient shell.

### Switching modes (`LANG_SWITCHER_MODE`, config, default `"off"`)

| Mode | Visible switcher | `?lang=` works |
|---|---|---|
| `off` | no | no — ignored outright, even with a crafted URL |
| `nav` | yes (nav.js) | yes |
| `secret` | no | yes, undocumented |

The MECHANISM is identical for `nav` and `secret` — `i18n.handle()` intercepts `GET <any path>?lang=<code>` (mounted early in `routing.py`'s `GET` list, right after `legacy_urls`/`demo_installation`, before `patient_web/site_*.py`), sets the `lang` cookie (1 year, `Path=/`, `SameSite=Lax`), and 302-redirects to the same path with the query stripped. The native `patient_site_router` performs that exact interception before its turnos module gate and forwarding adapter, so a valid switch keeps the same redirect/cookie ordering even while turnos is disabled. The only difference between the two modes is whether a UI element points at that URL. `off` mode makes `i18n._maybe_switch_lang()` return `False` unconditionally — the URL trick can't expose a feature the installation didn't opt into, and with `<2` enabled languages it's also a no-op regardless of mode (nothing to switch between).

The public demo seeds `es,en`, defaults newcomers to `es`, and uses `nav`; its shared demo bar renders the same
ES/EN links on public, account and admin surfaces. Admin body copy is still
Spanish-only: `booking_requests._serve_admin()` resolves the cookie only for
the injected `<aside lang=...>`, leaving `admin.html`'s own `<html lang="es">`
truthful. This is navigation-language continuity, not a claim that the admin
application has been translated.

**`nav` mode's visible switcher** lives in `nav.js` (`langSwitchHtml()`): a `<div class="stznav-langs">` rendered as the LAST child of `<nav class="stznav-menu">`, so the languages sit on the same line as the rest of the menu items, flush right, and collapse into the burger with them (the product owner, 2026-08-01 — this revokes the phase-3a sub-row that hung under the bar as a sibling of `.stznav-inner`). Each language is a plain `.stznav-link` — the same control the other menu items use, same size, hover and green `on` pill for the active one — plus a `.stznav-lang` modifier that only tightens the horizontal padding. Being inside `.stznav-right` now, the switcher DOES count toward `layout()`'s burger-fit measurement, which is the intended behavior: it has to fit like any other item, and if it doesn't, the whole menu collapses. It only renders when `window.SANA_I18N` is present with `mode === "nav"` and `enabled.length >= 2`; `window.SANA_I18N` is injected via the `{{i18n_bootstrap}}` template token, opt-in per page (today: the four `site_identity.py` pages) — every page that DOESN'T carry the token gets `window.SANA_I18N === undefined`, so `langSwitchHtml()` returns `""` and nav.js's rendered markup is byte-for-byte what it always was. This is the "integrate minimally" scope cut this slice made deliberately: a sitewide `window.SANA_I18N` injection (so the switcher shows on every page, not just the proof page) is extraction-fan-out work, not core-slice work — see below.

### The client module (`static/platform/i18n.mjs`, `GET /api/i18n/<lang>.json`)

`GET /api/i18n/<lang>.json` (`i18n.py`'s own route) serves the merged catalog for a language, ETag'd (sha256 of the body, first 16 hex chars) with `Cache-Control: public, max-age=300` and a real `304` on a matching `If-None-Match`.

`static/platform/i18n.mjs` is the canonical client lookup (`t(key, vars, fallback)`, same fallback contract as the Python `t()`: missing key → the fallback if supplied, else the key itself, never blank). It auto-boots synchronously from `window.SANA_I18N.catalog` — configuration data the server inlines via `bootstrap_script()` — so `t()` is correct from first paint. Consumers dynamic-import it through `window.SANA_STATIC["platform/i18n.mjs"]` and await that promise at their boot/render boundary. There is no `window.SanaI18n` global and no classic `i18n.js` twin.

A page served in the canonical language ships an empty catalog; call sites pass the Spanish literal as `fallback`. A non-canonical page inlines the full catalog so English (etc.) is correct before any network fetch. A failed `load()` fetch adopts `{}` and still resolves.

## `translate.py` — pack content

### Cache contract (table `translations`, Alembic baseline)

```
(source_key, lang) -> {source_hash, content, model, override, created, updated, updated_by}
```

- `source_key` names WHAT is being translated (e.g. `"preparation.laboratorio-sangre.resumen"`) — stable across content edits, so re-translating replaces the row instead of orphaning a stale one under a new key.
- **Reuse until `source_hash` changes.** `translate(source_key, text, lang)` hashes the CURRENT source text (sha256, first 24 hex chars) and only returns the cached row when the hash matches. Toggling a visitor's language back and forth is always a cache hit after the first translation — **zero model calls**, proven in `tests/test_translate.py`'s `test_toggle_twice_is_one_row_zero_calls_on_second_toggle`. A content edit changes the hash → the next request for that `(source_key, lang)` re-translates.
- **`override=true` wins regardless of `source_hash`** — an admin's manual correction (`translate.set_override(source_key, lang, content)`, a write path this slice ships but doesn't attach an admin UI to yet) always beats the machine output, exactly like a `catalog` DB row overriding its JSON base. `translate.clear_override(source_key, lang)` deletes the row entirely, restoring the machine path (same "restore = delete the override row" contract as `catalog_delete_row`/`prompts.prompt_delete`).

Migration 002 is a pure `CREATE TABLE IF NOT EXISTS` — unlike 001 (a RENAME, which needed `information_schema` existence checks to stay safe across "already migrated" vs "never had the old name" states), a brand-new table's idempotency comes for free from the `IF NOT EXISTS` guard itself. Safe on a fresh DB, an already-migrated DB, or run twice in a row — `tests/test_translate.py`'s `MigrationIdempotencyTests` exercises all three.

### The gate: `localized_text()`

```python
translate.localized_text(source_key, text, lang, pack_lang=None)
```

`pack_lang` defaults to `translate.pack_language()` — the active pack chain's HIGHEST-level pack's own `pack.json:language` field (`"es-AR"` for `ar-b-pinamar`, normalized to its primary subtag `"es"`). **When the requested `lang` already matches the pack's own language, this is a complete no-op**: no DB row, no model call, the original text returned untouched. Only a genuine language MISMATCH triggers `translate()`. This is the "requested lang ≠ pack language" check the phase 3 plan calls for — it's what keeps a single-language installation (or a request for the pack's own language on a multi-language one) from ever touching the translation machinery at all.

### Proof surface: preparation summaries

`translate.localized_preparation_summary(item, lang, pack_lang=None)` wraps `catalog.preparations()` entries (`id`, `resumen`) — the one sentence patients read on `/upload-order` and the preparation pages ("se hace con ayuno...", "traé tu orden y tu DNI..."). **Not wired into any live page** — this proves the cache + gate work end to end against REAL pack content (`tests/test_translate.py::test_localized_preparation_summary_proof_surface`), the same "prove it, don't sweep it" scope the UI-string proof used for `about.html`. `scripts/translate_pack.py --lang en [--dry-run]` is the warm-up sweep over this one surface — re-run any time, a no-op (zero model calls) for every entry whose `resumen` hasn't changed since the last sweep.

### Why JS literals are still untouched

Investigated before writing any `SanaI18n.t()` call site into a real page (task instruction was to wire JS strings via the shim). Found a correctness gap that makes it unsafe to do casually:

`i18n.js`'s `load()` always does an **async** `fetch("/api/i18n/<lang>.json")` on script load — `bootstrap_script()`/`{{i18n_bootstrap}}` only injects metadata (`active`/`enabled`/`mode`/`default`), never the catalog itself (`window.SANA_I18N_CATALOG`, the inline-injection path, has no caller yet). Until that fetch resolves, `SanaI18n.t(key)` falls back to **the literal key string** (`makeT()`'s fallback contract), not to any hardcoded Spanish. If a page called `SanaI18n.t()` synchronously (e.g. inside a script that runs at parse time, or on a user interaction that can plausibly fire before the fetch settles — page reload with a cold cache, slow connection, offline-first scenarios), a visitor could see a raw dotted key like `home.results.empty` flash or render instead of real text — on the DEFAULT single-language install too, since `i18n.js` always fetches regardless of whether `LANGUAGES` is configured.

This breaks the invariant every other part of this slice leans on: **i18n must be a true no-op, zero added risk, on an installation that never opted in.** The Python side gets this for free (`t()`/`raw()` read the catalog synchronously off disk, with an in-process mtime cache — no network, no race). The JS shim has no equivalent guarantee yet.

Fix needed before converting any interaction-triggered JS literal (not investigated further this slice — flagging for whoever picks this up next):
- Either have `bootstrap_script()` inject the ACTIVE lang's full catalog inline (`window.SANA_I18N_CATALOG`) on every page that loads `i18n.js`, so `SanaI18n.t()` is synchronously correct from first paint (no fetch race) — the "future slice" hook `i18n.js`'s own docstring already mentions, or
- Change `makeT()`'s fallback so an untranslated/not-yet-loaded key falls back to a caller-supplied default string (the hardcoded Spanish) instead of the raw key, mirroring the Python `raw()` fallback chain (lang → es → key) more conservatively (lang → inline-default → key).

Until one of those ships, static server-rendered `{{t.*}}` content (Python side) is safe to keep extracting; live JS-rendered strings are not.


## Request-scoped language (`i18n.bind` / `i18n.active`)

`resolve_lang(handler)` needs a handler. Almost nothing that renders has one: `site_shell._shell()` is called by ~20 functions across five modules, each holding only its own data, and threading a handler down all of those to reach the single line that writes `<html lang>` would be a very wide change for a value that is constant for the whole request.

So `routing.dispatch()` resolves it once, stores it in a `ContextVar`, and resets it in a `finally`. A ContextVar rather than a module global because the server is threaded — each thread gets its own value — and the reset matters because a recycled thread must never hand a visitor's language to a daemon render.

Anything that renders calls `i18n.active()`: the canonical language when nothing bound one, which is what tests and background jobs get.

`i18n.t_or(key, default, lang)` is the Python twin of the JS shim's third argument: the catalog when it has the key, the caller's own literal when it doesn't. It exists so a call site that already holds the canonical string doesn't have to round-trip through the catalog to render unchanged.

## Four defect classes the whole-site translation pass (2026-08) shipped repeatedly

The mass extraction sweep (patient site + admin panel, ~31 PRs, ~29 parallel agents) hit the same four bug shapes over and over, each one invisible from the Spanish-canonical browser it was written in — none of them fail a test, they just render the wrong thing in the OTHER language. Read this before extracting another surface.

**1. A module-level constant holding translated text freezes at import.** `i18n.t_or()` reads `i18n.active()`, and `routing.dispatch()` only binds a real language once a request exists. A constant built at module load time — `_DOCTORS_COLS = _centro_medicos_cols()` written once at the top of the file, instead of a function called per render — captures whatever `i18n.active()` returns with NO request bound, which is always the canonical language. The result renders correctly for the person who wrote it and wrong for everyone else, forever, with no error anywhere. This shipped ten-plus times: `site_listing.py`'s doctor/study table headers and mode/category labels, `reports.py`'s weekday and month names and rejection-group labels, `settings_admin.py`'s integrations registry. The fix is the same everywhere — turn the constant into a function called inside the render path, exactly like every OTHER table on the same page already does (`site_listing.py:2087-2093` documents the exact bug next to its own fix, left in place as a guardrail for the next person tempted to hoist it back out). **Client-side JavaScript has the same readiness hazard.** A full-page language reload does not make a dynamic import synchronous. Derive translated labels after the native i18n promise resolves, or lazily at a render boundary that awaits it. Delay the actual module response in a browser test and inspect the first visible labels; network-idle text assertions cannot prove first paint.

**2. Never key logic on a field's rendered/translated text — key on its wire value.** Once a field is in `pack_l10n.FIELDS`, comparing against its rendered string only works in the pack's own canonical language; the comparison breaks silently, in every OTHER language, the moment translation kicks in. Four instances: `listing.js`'s `COLAPSA` table and `site_listing._doctor_audience_sex()` (see below, both now key on `kind`/cluster id instead of the specialty label), `_workshop_note()` (used to parse a hardcoded Spanish marker out of the translatable `cartel` field — fixed by giving the note its OWN untranslated-shape field, `site_page_centers.py:4268-4281`), and a preparation-instructions lookup that matched against a service's rendered name — on an English page it would have compared an English name against a Spanish key and silently produced no match, hiding fasting instructions. Always match on the id/slug/kind the pack already carries, never on the string a visitor reads.

**3. Never concatenate a translated word with a formatted date, weekday, or month.** This is the bug that started the whole project: a live page rendered "Sacar on mañana, 08:00" — a Spanish verb, an English preposition, and a Spanish day name, because a Spanish grammar rule (`"el " + lowercase(weekday)`) ran unconditionally over text that was already in English. Grammar — which article, whether to lowercase, word order — is language-specific, not a string operation you can bolt onto formatted output after the fact. The fix is one catalog entry per WHOLE phrase with a `{when}`-style variable (`i18n.t_or("...", "...", lang, when=fecha_formateada)`), never a template that assembles a sentence out of separately-translated pieces. Related: English weekday/month names are always capitalized; Spanish lowercases them mid-sentence — that casing rule lives with the language, not as a global default the caller can assume.

**4. A translation key present with an empty string ("") is a REAL translation, not a missing one.** `_client_catalog()` used to filter the merged catalog with `{k: v for ... if v}`, and `i18n.js` had the identical flaw. `date.article` is `""` in English and `"el"` in Spanish — a legitimately empty English value — so filtering on truthiness dropped it and English pages inherited the Spanish article. `_client_catalog()`'s current comment (`i18n.py`, next to `merged.update(...)`) spells out the fix: filter a merged catalog on **key presence**, never on whether the value is falsy. `raw()` had the same bug on the server side, fixed the same way.

## `pack_l10n.py` — which pack fields are content

`translate.py` can translate any string; `pack_l10n.py` decides WHICH. It holds the field map (`FIELDS`) and the one function that walks a loaded pack row swapping them, and `patient_web/site_*.py`'s four loaders (`_services`, `_centers`, `_clusters`, `_doctors`) call it. Four rules the map encodes, each one a bug avoided:

- **Names of people and places stay put.** A center is "Sampleton Regional Hospital" in every language, and so is its address.
- **A service's search vocabulary (`palabras`) IS translated (2026-08-04)** — the one exception, per the product owner: "if the page is in English, the chips are in English, searches in English, and results in English." `palabras` is a LIST of short terms, not a sentence, so it's translated term by term via the same list-field walk `entries()`/`localize()` already had (see below) — the English list is free to carry both spellings where they differ ("ultrasound"/"sonogram") since redundancy in an index is free recall. The home page's example search **chips** still stay in pack language (`site_identity.search_examples_html`, `scripts/search_examples.py`) — those are literal queries proven against the Spanish catalog, a different concern from the vocabulary a translated query is matched against.
- **Identifiers stay put.** `id`/`slug`/`cluster`/`categoria`/`modo` are wire values.
- **Strings the code PARSES stay put.** `horario` ("Lunes a viernes de 08:00 a 12:00") reads like prose but feeds platform/hours.mjs/platform/week.mjs's Spanish day parser; translating it would empty the weekly grid. Same for `consultorio` (a room code rendered after a separately-translated label) and `sede` (a venue name).

Two Spanish-coupled algorithms had to move off translated text at the same time: `site_listing._doctor_audience_sex()` now reads the cluster id (`gineco`, `pediatria`) before the specialty label, and `listing.js`'s collapse table (`COLAPSA`) is keyed on the `kind` the server sends instead of the rendered Spanish.

Reads go through `translate.cached_text()`, **never** `localized_text()`: a page renders hundreds of pack strings and translating them inside the request would put hundreds of sequential OpenRouter round trips in front of the first byte. A cache miss degrades to the pack's own language for that one string.

## The ten shipped languages and the generated catalogs (2026-09-11)

`i18n.LANGUAGE_NAMES` is the shipped set — `es en pt fr it de ru uk ja zh`, the same ten humanrounds.org and Bruno offer, each with its own name for switcher labels (`i18n.language_name(code)`; the admin Settings screen and the demo bar read it from there, nothing translates the list). Codes are **primary subtags only**: `Accept-Language` is reduced to its primary subtag, the cookie carries what the switcher sent, and a `pt-BR` catalog directory would simply never be found by a `pt` request.

`locales/es/` is canonical and `locales/en/` is hand-kept; **the other eight are generated** by `scripts/translate_locales.py` from those two (Spanish for meaning and register, English as a pivot), through the same OpenRouter model `translate.py` uses for pack content — JSON in, JSON out, 40 keys a call, placeholders/tags checked per key, a mismatch retried and then left out (a missing key falls back to Spanish at render, visibly). It is incremental: `locales/<lang>/_source_hash.json` remembers the Spanish each key was translated from, so after touching 20 canonical strings a re-run costs 20 strings. **Never hand-edit a generated catalog** — the next run overwrites it; fix the Spanish (or the prompt) and re-run. The generic mode (`--json in.json --lang it --out out.json`) is what humanrounds.org's copy goes through (`intake/app/scripts/extract-copy.mjs` → `i18n-flatten.mjs` → this → `build-i18n-extra.mjs`).

**The public demo enables all ten and sets NO explicit default** (`seed_demo_all._seed_language_config`, re-applied on every deploy): with `LANG_DEFAULT` empty, step 3 of the resolution order — `Accept-Language` — decides for a newcomer, so an Italian browser reads the demo in Italian, and a visitor arriving from humanrounds.org's Italian page lands on `demo.humanrounds.org/?lang=it`, which sets the cookie and redirects clean. The footer link back to humanrounds.org carries `?lang=<active>` the other way (`templates/_site_footer.html`), so the two sites never disagree on the visitor's language. A production installation keeps its own explicit default; nothing here changes it.

The demo bar's switcher is a `<select>` of the enabled languages in their own names (`demo_installation._lang_switch_links`) — a row of ten two-letter codes no longer fit beside the three demo links on a phone, and `IT`/`UK` mean nothing to the person who needs them.

## Filling the cache

- `scripts/translate_pack.py --lang en` sweeps the whole pack (services — including each one's `palabras` search terms — centers, doctors, clusters). `translate.translate_batch()` sends 40 strings per model call and falls back to one-at-a-time when the numbered response doesn't line up — a mis-aligned batch would label a cardiology service as a blood test, which is worth paying to avoid. An UNANSWERED batch is not a mis-aligned one: when the provider does not answer the batch call at all, that batch is skipped whole and waits for the next sweep instead of 40 more failed single calls (2026-10-23). The demo pack is ~400 strings in ~12 calls.
- `translate_warmup.py` runs the same sweep as a daemon, every 6 h, and `start()` returns False unless a second language is enabled — so it does not exist on a single-language installation. Since Tier 4 daemon batch 3 (2026-08-08), with `TURNOS_QUEUE_WORKER` set the sweep runs in the queue worker instead (`app/ops/translate_warmup_queue.py`, registry entry `translate_warmup` in `worker._JOBS`, `outbound=True`) and the web process starts no thread. Two contracts worth knowing there: language eligibility is re-resolved on EVERY tick (`pending_languages()` inside the sweep body — enabling a second language from the panel reaches the next sweep without a worker restart; the registry-level OFF is only `TURNOS_TRANSLATE_WARMUP_OFF`), and each worker boot defers one startup sweep keeping the thread twin's 30 s grace (durable `schedule_at`, the boot instant from `core.clock` + 30 s, queued-row dedup) so a cold install never waits up to 6 h for the first cron boundary. Both AI-cache sweeps register procrastinate's native per-job `lock` as their task default (`queue_infra.task_lock_name`) — cron, startup and recovery invocations serialize fleet-wide at fetch time; a concurrent second job waits and runs after, where the source-hash guard (run-twice proven) makes it a no-op — overlap spend is closed by the lock, and the only residual provider cost is the audited crash window (a death between the provider call and the cache upsert re-buys that one call).
- **Dead sweep found and removed (2026-08-04):** both sweepers used to also collect `catalog.preparations()`'s `resumen` field (`preparation.<id>.resumen` cache keys) — the phase 3a proof surface `translate.localized_preparation_summary()` exists for. That field doesn't exist at all in the demo pack (`packs/example-town/estudios-preparacion.json` — 0 of 30 entries carry it; the newer `antes`/`avisar`/`despues`/`no_hace_falta` structured sections replaced it there) and `localized_preparation_summary()` itself is called from no live page — grepping the whole tree for its name turns up only its own definition and `test_translate.py`'s proof-surface test. So the sweep was silently contributing zero strings on the one installation that matters (the demo) while its output line implied coverage. Removed from both sweeps rather than pointed at a substitute field: the real preparation text patients read is now composed server-side from several structured fields (`prep_model.py`'s `secciones()`/`ayuno()`), not one sentence, and translating that properly is the `estudios-preparacion.json` item already tracked below ("not actually translated+wired into a live preparation page") — not a one-line fix. `translate.localized_preparation_summary()` and its cache/gate mechanics stay in `translate.py`, still proven by `test_translate.py::test_localized_preparation_summary_proof_surface` against a synthetic item; only the two sweep scripts stopped calling it.

## `TURNOS_FAKE_TRANSLATE`

Per-feature escape hatch (`translate.py:_fake()`), same shape as `chat_agent`'s `TURNOS_FAKE_CHAT_AI`: read first, falls back to `TURNOS_FAKE_AI` when unset. Exists because `TURNOS_FAKE_AI` means "don't send a VISITOR's document/message to a provider" — translation has nothing to do with a visitor, it translates the installation's own already-public catalog, so a demo installation (which runs `TURNOS_FAKE_AI=1` for everything else) sets `TURNOS_FAKE_TRANSLATE=0` to keep using the real model for this one feature (`demo_installation.py`). Leaving it unset on an installation that has `TURNOS_FAKE_AI=1` and a second `LANGUAGES` entry poisons the cache: every pack string translates to the literal `"[en] Clínica médica"` marker, and because that fake row's `source_hash` matches, a LATER real sweep sees nothing stale and never overwrites it — `translate_warmup.py`'s `_drop_fake_rows()` is what makes that self-healing (deletes the `[<lang>] …`-prefixed rows once `_fake()` is false), but it only runs once the flag is actually flipped. See `.env.example`'s Languages section for the var itself, and [i18n-content-translation-traps.md](../solutions/dev/i18n-content-translation-traps.md) for the incident this fixed.

The AI instructions editor (`prompts.py:_fake()`) reads the same switch since 2026-11-15: those instructions are the installation's own text, so on the demo the «Español» tab gets a real translation instead of «[es] <the English>»; a cached translation with any paragraph carrying the fake «[es] » tag is redone once `_fake()` is false.

## Why JS literals were untouched (fixed 2026-08-04)

The old blocker: `i18n.js` fetched the catalog asynchronously, so `SanaI18n.t(key)` returned the raw dotted key until it landed, and a page could flash `home.results.empty` at a visitor.

Both halves of the fix:

- **`t(key, vars, fallback)`** — the third argument is the literal the call site replaced. With no catalog at all, every converted string renders exactly the bytes it rendered before it was translated.
- **The catalog is inlined** in `bootstrap_script()` for pages served in a NON-canonical language, so `t()` is correct at first paint. A page in the canonical language ships no catalog: the fallbacks already say it, and shipping it would put every interface string of the site into the HTML of every page.

`tests/i18n-fallbacks.test.mjs` enforces the contract — every `T(...)` call passes a fallback, and every key it names exists in `locales/es.json`. Without it the bug is invisible to a developer, who browses in the language the catalog is canonical in.

Converted so far: `nav.js` (which also lost its own inlined es/en table — a second translation mechanism for one file), `listing.js`, `static/platform/directory.mjs`, `index.html`'s inline script, and `site_shell`'s column registry and page copy. `{{i18n_bootstrap}}` is no longer opt-in per template: `_shell()` emits it on every page it builds.
