# Routing and module ownership

Extracted from CLAUDE.md 2026-07-29 (verbatim). These are load-bearing decisions — **do not relitigate** what is marked as such. Read this file before touching the code it describes.

> **Status 2026-08-27 (native-migration final wave):** the legacy dispatch
> machinery this file describes (`server.py`, `routers/legacy_http_transport.py`,
> `ops/legacy_web_server.py`, `core/routing.py`'s GET/POST/PUT/DELETE registry
> + `dispatch()`, `legacy_shim.py`, `services/legacy_http.py`,
> `services/legacy_static.py`, `core/module_router.py`) has been **deleted**.
> The native FastAPI composition (`app.py`, served by `asgi_main.py`) is the
> only topology; module route ownership lives in each `module.json`'s
> `router_attr` entries mounted by `app_modules.mount_module_routers()`, and
> platform-core routers in `app/routers/platform.py`'s ORDERED tuple. The
> sections below remain as the authoritative history of the retired design
> and of the ownership decisions that still apply (which module owns which
> surface). Feature modules' `handle(handler, method)` transports were deleted
> too (2026-08-30/31; `test_asgi_main_dark_mode_retirement` pins the
> retirement).

**Phase 6a runtime slice (2026-07-30):** `routing.py`'s `dispatch()` no longer just walks the ordered `GET`/`POST`/`PUT`/`DELETE` literals below unconditionally — it skips any handler whose owning app module (`app/modules/<id>/module.json`'s `"routes"` list) is currently disabled, via `app_modules.route_enabled()`. The lists, their exact order, and every module named in this file are unchanged; what changed is that a disabled module's handlers are now genuinely never called. Full detail, the `ENABLED_MODULES` config key, and `manage.py mod enable/disable` → [docs/modules.md](../modules.md).

- **Tier 4 (`docs/roadmap/tier4-replatform-design.md`) added a second, FastAPI-shaped route registration that coexists with everything below, unchanged.** `app.py` mounts `app_modules.mount_module_routers()`'s FastAPI twins (a `module.json` route entry's `router_attr`, a sibling `*_router.py`) plus platform-core routers mounted directly; a final native terminal owns dynamic pages, static assets, and bounded compatibility errors. The demo has used `TURNOS_ASGI=1` since 2026-08-08; on 2026-08-19 current Coolify configuration and exact-SHA deployments verified the same topology on production `pinamar.humanrounds.org`. `server.py`'s own dispatch remains the dark rollback contract, and every route this file describes is owned by the native ASGI composition. Don't add a new legacy route without checking whether it needs one.
- **The terminal's static fallback serves an explicit list (2026-11-12).** `/static/...`, `/vendor/...`, `/webdata/...` and `/data/...` (their own rules), the root web assets of `app/core/paths.py` (`/admin-app.js`, `/logo.png`, ...), and the module assets a `module.json` declares; any other path — source, tests, documents, templates — is a 404 whether or not the file exists, a dot segment (`/.env`) stays 403. Before, any checkout file with a public-looking extension was served. Where each served path lives on disk: `services/static_assets.disk_root()`. Pinned by `tests/test_static_allowlist.py`.
- **server.py is the 33-line stable legacy entrypoint; do NOT add features to it.** `routers/legacy_http_transport.py` owns the concrete compatibility handler and delegates to the modules that own their routes: `patient_web/site_*.py` (patient flow: home data, `/service/<id>`, `/service/<id>/book`, `/centers`, `/center/<slug>`, `/my-requests`, `/api/services`, `/api/centers`, redirects), `availability_directory.py` (read-only legacy snapshot projection and canonical `GET /api/specialties`; its sibling router owns that ASGI path directly while `/api/especialidades` deliberately remains a legacy URL rewrite), `solicitudes.py` (backend: `/api/requests`, `/api/analyze-order`, `/admin`, `/api/admin/*`), `cuentas.py` (`/account`, `/api/account/*`), `calendario.py` (ICS: `GET /api/appointment/<id>.ics` a single appointment, `GET /api/calendar/feed` returns the logged-in user's feed URL, `GET /feed/appointments/<token>.ics` public feed of all future approved appointments — the token IS the authentication), `preparacion.py` (`/upload-order` — `/api/preparacion` DIED 2026-07-16, the client uses `/api/analyze-order`) and `puco.py` (`/api/puco`: health coverage by DNI against the SISA registry). `handle(handler, method) -> bool`. New features = a new module or these, never the entrypoint. ICS event title = "{servicio} en {centro}"; LOCATION = the center's address; DESCRIPTION carries the patient's name (to recognize the appointment on a shared calendar). Event local time is ALWAYS converted to America/Argentina/Buenos_Aires (-03:00 fixed, no DST) regardless of the timezone `turno_dt` arrives in from Postgres — the process runs with the system's TZ (`America/New_York` was seen in dev, hence the raw `-04:00` that showed up in "Mis solicitudes" before the friendly-format fix), so trusting the offset as it comes from the column, as-is, is a bug. Feed tokens (`users.feed_token`, `operators.feed_token`) are stored as a SHA-256 hash plus `feed_token_hint` (last 4 chars), formula in `app/core/feed_tokens.py`: the full address is returned once — when `GET /api/calendar/feed` (or the doctor's `/api/admin/my-appointments/feed`) issues the token, or on `POST /api/calendar/feed/regenerate` / `…/feed/rotate` — and afterwards only the hint (2026-11-06 decision).
- **The private-doctor directory (WebTurno) was removed from the UI, not from the code.** Private clinics were taken off the site (the product owner, 2026-07-08: "it's only for Hospital Pinamar"): `/clinicas`, `/clinica/*`, `/directorio`, `/obras-sociales`, `/cobertura/*` → 302 to `/` from `patient_web/site_*.py.handle` (runs before server.py's legacy routes, without editing server.py). The WebTurno code in server.py stays dormant; do not revive it for the hospital. **Dated correction (2026-08-18):** the "stays dormant" framing describes the state before the bounded server.py retirement series. The coverage pages (`/cobertura/*`, `/obras-sociales`), the private doctor directory (`/medicos`, `/medico/<slug>`), the private clinics pages (`/clinicas`, `/clinica/<slug>`), and the dormant WebTurno CLIENT surface (owner/patient login, availability, booking, calendar, vault, coverage — see below) have all been DELETED from server.py, not left dormant — each de-linked path is proven dead in both transports before its dispatch block and renderer are removed. The live clinics DATA path (`especialidades_tree()`, `all_clinicas()`) now lives in `patient_web.availability_directory`; `/datos` is rendered by platform-core `patient_web.health_data`, with only a late delegation left in `server.py` to preserve registry precedence. See `docs/roadmap/server-retirement-slice4-clinicas.md`.
  - **Retirement slice 3b (2026-09-05) physically deleted the dormant on-disk clients** — `app.html`, `panel.html`, `directorio.html`, `ui-core.js`, and `specialty-browser.js`. The public page routes remain 302s to `/` (query dropped, no `Cache-Control`). The `/stz-ui.js` and `/rubricador.js` rewrite entries are closed. A dropped-back copy of those scripts is denied by the native terminal the same way `admin.html` is.
  - **Retirement slice 3 (2026-08-16) deleted the dormant WebTurno CLIENT surface from server.py for good** — the app.html/panel.html patient/owner client and its whole header-credential API (`GET/POST/DELETE` on `/api/login`, `/api/whoami`, `/api/availability`, `/api/appointments`, `/api/refresh`, `/api/book`, `/api/cancel`, `/api/watch[/state]`, `/api/calendar[/status]`, `/api/confirmation`, `/api/logs`, `/api/vault`, `/api/owner/coverage[/*]`, plus the `/app` and `/panel` rewrites), the boot-time owner login + `ops/watcher.py` vigilante daemon, and `notifications/gmail_confirm.py`. Those endpoints now fall to server.py's generic `/api/` 404. Reachability argument and pins: `tests/test_server_webturno_retirement.py`. **Ownership after the slice:** identity/session → `cuentas`/`auth` (the retired surface violated "identity comes from the session, never the request"); booking → `app/modules/turnos`; the WebTurno integration itself → `app/connectors/webturno` (unchanged, still the slot-source connector with `manage.py conn`); the demo's deny-list (`ops/demo_installation._blocks_legacy`) is deliberately untouched and keeps hard-404ing the same inventory, so demo behavior is byte-identical and a rollback re-lands behind the same denial. The legacy `data/availability.json` snapshot is read-only: `patient_web.availability_directory._load_db()` feeds the live `/api/specialties` + `/<esp-slug>/<name-slug>` data path; nothing writes it anymore.
