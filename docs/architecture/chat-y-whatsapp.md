# Booking chat: engine, widget, WhatsApp

Extracted from CLAUDE.md 2026-07-29 (verbatim). These are load-bearing decisions — **do not relitigate** what is marked as such. Read this file before touching the code it describes.

- **The patient's MCP token is stored only as its SHA-256 hash (2026-11-06, Alembic 0038).** `users.mcp_token` holds the hex digest, `users.mcp_token_hint` the last 4 characters; `db_accounts.user_by_mcp_token` looks the Bearer up by its hash. The plaintext exists only in the answer that created it (`mcp_token_issue` on an account without one) or rotated it (`mcp_token_regenerate`); afterwards `GET /api/account/mcp` gives `token: null` and the hint, and «Mi cuenta» shows `••••` plus the hint. Neither column ever leaves through `_user_public` or the personal-data export. Never store, log or return the raw token again.
- **Booking chat: one engine, three doors (2026-07-23).** The MCP tool registry (`search_services`/`available_appointments`/`request_appointment`/`my_requests`/`cancel_request`, plus new `whoami` and `analyze_order`) moved OUT of `mcp_api.py` into `chat_tools.py` — a shared `TOOLS`/`TOOL_FNS` registry (each tool `fn(usuario, args, handler)`, identity always injected, never read from the body) so MCP, the on-site widget, and WhatsApp stop triplicating logic; `mcp_api.py` now just does JSON-RPC framing over `chat_tools.TOOLS`/`TOOL_FNS`. `chat_tools._Shim` (moved from mcp_api) fakes a request handler for `solicitudes._create`/`_cancelar` — real `.headers` for MCP, `{}` for the in-process engine (both support `.get`, which is all `sitio.base_url` needs). `request_appointment` now accepts `orden_token`: a `solicitud_con_orden` service is blocked WITHOUT one (same as before) but bookable WITH a token from `analyze_order` — `solicitudes._create` already accepted `orden_token` for the web wizard, so this is just wiring, not a new gate; `walkin`/`walkin_con_orden` stay blocked always, token or not.
  - **`chat_agent.py`** is the multi-turn engine: a tool-calling loop (`messages[]`+`tools[]`, OpenAI/OpenRouter format, cap `MAX_ITER=6`) against `TURNOS_AI_MODEL` (default `google/gemini-3-flash-preview`) via its own `_call_chat` (ai_orden's `_call_openrouter` is single-shot, no tools). `usuario=None` (anonymous) restricts tools to `ANONYMOUS_TOOLS` (search + slots only — no booking, no whoami, no analyze_order); a tool the model requests outside that set is refused in code, never executed on a guess. `TURNOS_FAKE_AI=1` drives a deterministic fake model (`_fake_step`): a user message `"TOOL:<name>:<json args>"` triggers that tool call once, `"MARKERS:<texto>"` makes it echo `<texto>` verbatim (markers included, for testing extraction), anything else is a plain echo — enough to test the loop/persistence/auth wiring without a real model. Conversation persists to Postgres `chat_mensajes(canal, clave, rol, contenido jsonb, created)` — `contenido` is the WHOLE OpenAI-shape message (round-trips straight back into `messages[]`, no reassembly); best-effort (`db_chat.chat_save_message`/`db_chat.chat_history`, last 20 turns), never blocks a reply. **Marker protocol (2026-07-23, feedback from the product owner's first real chat: the assistant answered a "when are cardiology appointments" question with a counter-question instead of listing everything it knew).** `_COMPACT_SYSTEM_PROMPT` now requires answering FULLY before asking anything ("never answer a question with only a question"; a closing question is only allowed AFTER the information is given) and only light formatting (`**bold**`, `* ` bullet lines — no headings/tables/markdown links). When offering concrete choices (centers/days/slots) the model closes the message with `[opciones: A | B | C]` (2-6 short labels); `[login]` anywhere in the reply signals the person needs to sign in to continue. `_parse_markers` extracts+strips both (regex, tolerant of whitespace) — `_run_turn` (the renamed original loop) returns the RAW text with markers still in it and persists that raw text to `chat_mensajes` at every step (the model needs to see its own past `[opciones:...]` in history to understand a reply like "1"); only the text handed back to a channel is stripped. `chat_full(usuario, texto, clave, canal) -> {"texto","opciones","login"}` is the full contract (chat_api.py: the widget renders chips + an inline login button); `chat(...)` (unchanged signature, used by whatsapp_chat.py) calls `chat_full` and flattens it back to plain text — options become a numbered list appended to the message ("1. …", "2. …", no chips on WhatsApp), `[login]` is dropped silently (WhatsApp identity is the phone, not a login flow).
  - **On-site: `chat_api.py` + `static/platform/chat-widget.mjs`.** `POST /api/chat {mensaje}` — `cuentas.accounts.current_user` decides full vs. anonymous; `clave` = `"dni:<dni>"` logged in, `"ip:<ip>"` anonymous (own per-IP rate limit `TURNOS_CHAT_PER_HOUR`, default 60, abuso.py-style window but its own bucket). The widget is a floating launcher mounted next to `nav.js` on public pages and on `_shell` default/`chrome="focus"` (`app/cuentas/accounts.py` `/account`, `index.html`, `about.html`, terms, privacy) — **not** on `chrome="chat"` interview pages (two chats on one screen would confuse). `static/platform/chat-widget.mjs` is content-hash fingerprinted (`static_fingerprint.CLIENT_LOADED` / `MIGRATED`; pages bootstrap it through `templates/_chat_bootstrap.html`, never an unversioned URL). **Round 2 (2026-07-23, the product owner's feedback on the first real chat):** the response now carries `opciones`/`login` from `chat_agent.chat_full` (omitted when empty/false) — the widget renders `**bold**`/`* ` bullets as real HTML (escape first, then bold, then list — no lib) and paints `opciones` as a row of tappable chip-buttons under the assistant's message (10px-radius rectangular buttons, NOT full pills — related-control layout hook: one coherent group, consistent height; clicking one sends its label as the next message and removes the row). `login:true` renders an inline "Iniciar sesión" button that dynamically loads `account-form.js` (classic `<script>`, URL resolved through `window.SANA_STATIC` — `static_fingerprint.CLIENT_LOADED`, fail-closed: no entry → the "No pudimos cargar el inicio de sesión acá" notice with the link to Mi cuenta) and mounts `window.SanaAccount.renderAuth(host, {defaultMode:"login", onDone})` INSIDE the panel in a `.stzc-auth` section below the messages (panel widens to 440px while `.stzc-panel--auth` is active — `renderAuth`'s `.sc-authform` wants 480px, doesn't fit in the default 360px) — the chat never navigates away; `onDone` tears the form down, restores width/the compose form, and adds an assistant bubble ("Listo, ya estás con tu cuenta. Sigamos."). New: a paperclip attach button (`accept="image/*,application/pdf"`, no `capture`) plus Ctrl/⌘V paste-an-image into the input, both send `{adjunto:{filename,mime,data_b64}}` in the POST body (shown client-side as a "📎 <filename>" user bubble). The header's `border-bottom` and the form's `border-top` were removed (the product owner, divider hook: bubbles + the input's own border already separate the regions) in favor of padding. New greeting + 3 starter chips (Buscar un servicio / Ver horarios / Subir mi orden — the last opens the file picker, not a message). **Round 3 (same day, product owner): the WhatsApp handoff moved to a top info bar** — `.stzc-wa`, a slim `--accent-soft`-tinted bar under the header and above the messages (background contrast, not a divider line) with a text link "Seguí esta conversación por WhatsApp" (ui-rules: link, never a button); painted ONCE as soon as a response carries `whatsapp` (guarded on `waEl.hidden`) and stays stable across turns instead of re-rendering every reply.
  - **`chat_api.py` adjunto + history adoption + transcripts export (2026-07-23, same round).** `POST /api/chat` accepts an optional `adjunto:{filename,mime,data_b64}` (cap ~8MB decoded, `solicitudes._decode_orden`) — the person can upload the order INSIDE the chat, not just via `/upload-order`. Logged in: analyzed through `chat_tools.analizar_orden_para("dni:<dni>", ...)` (same per-identity cooldown as WhatsApp/MCP) and narrated into the text the engine sees via the new shared `chat_tools.narrar_adjunto(texto, resultado)` — extracted out of `whatsapp_chat.py`'s inline narration so both channels stop duplicating it (whatsapp_chat.py now just calls it). Anonymous + adjunto: the engine is NEVER called and nothing gets analyzed — a canned reply asks to sign in first and sets `login:true` (don't burn AI on an order that can't be attached to anyone). **History adoption on login** (the product owner: "when I log in, it picks it from there"): on an authenticated request, `db_chat.chat_adopt_history("web", "ip:<ip>", "dni:<dni>")` copies the anonymous conversation's messages into the DNI conversation ONCE, only if the DNI conversation has no messages of its own yet (best-effort, never blocks). **`GET /api/chat-transcripts?hours=24` (cap 30 days)** is the export for the nightly prompt-learning job — `Authorization: Bearer <TURNOS_CHAT_EXPORT_TOKEN>`; env unset = the route doesn't exist (`chat_api.handle` returns `False` for GET, same fail-closed pattern as the WhatsApp webhook secret); wrong token → 403. Backed by `db_chat.chat_transcripts(hours)` (groups `chat_mensajes` by `canal,clave` for conversations with activity in the window; renamed 2026-09-15 — it used to share the name `chat_conversations` with the unrelated admin «Chats» list query and silently shadowed it). `chat_api.handle` is now wired into `server.py`'s `do_GET` chain too (it previously only ran on POST).
  - **WhatsApp: `whatsapp_chat.py` — TWO providers, ONE webhook (`/api/whatsapp/webhook`).** WAHA (self-hosted) and Meta's official WhatsApp Cloud API (the product owner's Meta test number, added 2026-07-23) both push to the same route; every inbound payload is normalized to one internal shape (`{from, from_me, is_group, body, media}`) before `_procesar_mensaje` ever sees it, so the rest of the module (handoff, engine call, reply) never branches on provider again. `_es_meta(body)` tells them apart by shape: Meta always carries `{"object":"whatsapp_business_account","entry":[...]}` at the root, WAHA never does. **GET** on the same route is Meta's webhook-verification handshake (`?hub.mode=subscribe&hub.verify_token=...&hub.challenge=...` → echo the challenge as `text/plain` if the token matches `TURNOS_WA_WEBHOOK_SECRET`, else 403; WAHA never sends GET here). **POST** auth: Meta's `X-Hub-Signature-256` (HMAC-SHA256 of the RAW body under the app secret `META_WA_APP_SECRET` — the only credential Meta ever sends, so the router reads the bounded body before authorizing; `whatsapp_chat.meta_signature_ok`, 2026-10-22) OR the shared secret `TURNOS_WA_WEBHOOK_SECRET` (header `X-Webhook-Secret`/`Authorization: Bearer`/`?secret=` — WAHA's way in); **both envs missing = the route doesn't exist** (`webhook_enabled()` false → 404), never an accidentally-open endpoint. The GET handshake still needs `TURNOS_WA_WEBHOOK_SECRET` as the verify token. Identity = the SENDER'S PHONE matched against `usuarios.contacto` by the last 10 digits (`db_chat.user_by_phone`) — 0 or >1 matches both resolve to "unknown" (ambiguous never guesses); writing from that phone IS the booking authorization, same pattern as the ICS feed token. `from_me`/group messages are ignored (WAHA: `fromMe`/`@g.us`; Meta: N/A — Cloud API never echoes outbound as `messages[]` and has no group chats, so those two flags are always false for it); a Meta `changes[].value` with only `statuses[]` (no `messages[]`) is skipped whole. A photo/PDF attachment resolves through a provider-specific downloader (`_descargar_media_waha`: WAHA's `media.url` + the same `X-Api-Key` as `otp_send.py`'s `waha_config()`; `_descargar_media_meta`: Meta's TWO-step `GET /<media_id>` (Bearer `META_WA_TOKEN`) → `{url}` → `GET` that url with the same Bearer) then runs through `chat_tools.analizar_orden_para` (neither provider has a native "tool call" for attachments, so the media resolves BEFORE the engine call and its result — `orden_token`/`veredicto` — gets narrated into the user's text so the model can act on it).
  - **Outbound is its own provider seam, independent of which provider the inbound message came from.** `otp_send.wa_provider()` (2026-08-14 transport contract: `meta` with an explicit `TURNOS_WA_PROVIDER=meta` pin or, unpinned, whenever `META_WA_TOKEN` is set; `waha` ONLY with an explicit pin AND an `OTP_WAHA_URL` pointing at loopback — a remote WAHA URL never sends, auto-detect never selects WAHA; anything else `""`/logged no-op) decides which transport `otp_send.enviar_texto()` uses for every chat reply — a deployment runs ONE active transport at a time, chosen by env, not by echoing the sender's provider. Meta send = free-form text (`POST /<phone_number_id>/messages {messaging_product,to,type:"text",text:{body}}`, Bearer `META_WA_TOKEN`) — valid because the patient always writes first, opening Meta's 24h service window, so no approved template is needed (contrast with the OTP send in this same repo — `otp_send.enviar_otp` behind `OTP_PROVIDER`, a different code path from `enviar_texto`: since 2026-11-16 `OTP_PROVIDER=meta` sends the code ONLY as the approved Authentication template named by `META_WA_OTP_TEMPLATE` (body `{{1}}` = the code plus the copy-code button, language `es_AR`; the Human Rounds WABA has `turnos_codigo`, approved 2026-11-16); without the variable it stays a logged no-op, and the WAHA sender keeps the loopback-dev-only restriction. No site enables it yet. The stale `codex/whatsapp-cloud-otp` branch is still not to be harvested).
  - **A Meta rate limit pauses EVERY Meta send (2026-11-16).** Codes 4, 80007, 130429, 131048, 131056, HTTP 429, or any `Retry-After` header open a pause of `Retry-After` seconds (60 s without it, 15 min cap) that a second limit never shortens; while it lasts nothing reaches the network (free text, Utility templates and the code alike — a logged no-op, the booking persists). The pause lives in `<data_dir>/private/meta-wa-state.json` so the web process and the queue worker share it (an exclusive `flock` plus an atomic replace; an unwritable volume falls back to the process's memory). «Sistema» → WhatsApp shows the pause until when and why, then «La pausa terminó» for a day. **An error code is read as words**: `otp_send._META_MOTIVOS` maps Meta's codes (131047, 132001, 190 and the common ones) to an i18n key with its Spanish fallback; the log carries `HTTPError (status) code — cause`, never Meta's own message; «Sistema» shows the last error for a day, red for the codes waiting does not fix (`otp_send.META_CODIGOS_GRAVES`) until a send succeeds again. Tests: `tests/test_meta_wa_limits.py`. Meta logs mask the phone to its last 4 digits and never print the token (`_mask_phone`); WAHA's existing `_enviar_whatsapp` logging was left as-is (unmasked) to keep this change's blast radius to the new path only.

  - **Web→WhatsApp handoff code (the product owner, 2026-07-23): transfers HISTORY; since 2026-08-02 also transfers AUTHORIZATION when minted by a logged-in session.** `chat_api.py` mints a short code (`db_chat.chat_handoff_create`, get-or-create per conversation `clave`, table `chat_handoffs`, 48h TTL) and returns it in every `/api/chat` response as `{whatsapp:{numero,link,codigo}}` **only if `TURNOS_WA_NUMERO` is set** — the widget renders it as a text link (ui-rules: never a button) to `https://wa.me/<numero>?text=<prefilled Spanish message with the code>` (works with any country's digits, incl. Meta's US test number `15556314211` — wa.me only cares about digits). **Code format hardened same day (round 2, product owner: "must be hard to guess"): `"ST-" + 12` uppercase-alphanumeric chars from `secrets.choice` (was 6 chars from `random`) — ~60 bits of entropy, up from ~30 (`db_chat._generate_handoff_code`/`_HANDOFF_LEN`).** `whatsapp_chat._CODE_RE` accepts 6-12 chars (not just 12) so any 6-char code already in flight when this shipped still binds until its 48h TTL expires — a deliberate compatibility choice over a hard cutover, noted here since it's a one-way door once no old codes are left. A WhatsApp message containing the code anywhere (`_extraer_code`) consumes it (`db_chat.chat_handoff_use`, single-use, atomic `UPDATE…WHERE usado=false AND expira>now()`) and COPIES the web conversation's messages into the WhatsApp conversation (`_copiar_historial_web`) so the person doesn't repeat themselves. **Authorization (the product owner, 2026-08-02: "I'm already logged in on the web, don't make me confirm my identity again on WhatsApp").** The phone match above (`users.contact`) is still the PRIMARY identity check and doesn't change. As a fallback, `db_chat.user_by_handoff_phone(tel)` looks at ALREADY-REDEEMED handoff codes: if the most recent one redeemed by this phone was minted by a LOGGED-IN session (`web_key` starts `"dni:<dni>"`), that account authorizes bookings from this phone for `TURNOS_WA_HANDOFF_GRANT_DAYS` (default 30) after redemption — so the person doesn't have to repeat the code on every later message. A code minted by an ANONYMOUS session (`web_key` starts `"ip:<ip>"`) never authorizes anything, no matter who redeems it — same as before. Invalid/expired code attempts are rate-limited per phone (`TURNOS_WA_HANDOFF_PER_HOUR`, default 8) so guessing codes isn't free, without ever blocking the rest of that WhatsApp message. **Arrival briefing (round 2, product owner): a successful redemption no longer answers with a fixed greeting.** `_procesar_handoff` now returns `(estado, mensaje)` (`"ok"`/`"invalido"`/`(None,None)`); on `"ok"`, `_narrar_arrival` weaves an instruction into the user's text — same pattern as the media path (`chat_tools.narrar_adjunto`): resolved BEFORE the engine call, not after — telling the model the person arrived from the web chat (whose history was just copied into this conversation's context) and to greet them, summarize in one line where things stood, and restate the last open question, instead of a canned line + a reply to whatever text carried the code.

  - **The way out to WhatsApp is ALWAYS on screen (the product owner, 2026-08-02).** It used to appear only once the assistant had answered — the response was what carried the `whatsapp` payload — so the first thing a person saw when opening the chat had no exit at all. Now `static/platform/chat-widget.mjs` asks `GET /api/chat/whatsapp` the moment the panel opens and shows the **code-less** link (`chat_api._handoff_abierto`); the first answer's `whatsapp.link` then swaps in the code-bearing one. Deliberately code-less until then: a code exists to carry HISTORY, someone who has not written anything has none to carry, and issuing one on every open would write a `chat_handoffs` row per idle visitor. With no `TURNOS_WA_NUMERO` the GET is a 404 and the control is not drawn at all — never a dead control.
  - **The on-site answer streams in instead of landing all at once (the product owner, 2026-08-02).** `POST /api/chat/stream` runs the EXACT same `chat_api._computar_salida` as `/api/chat` — same auth, rate limit, adjunto handling, `chat_agent.chat_full` call — so nothing about the answer itself changes; only how it is delivered does. This is progressive REVEAL of the already-finished text, not live model-token streaming: `chat_agent._run_turn`'s answer goes through jurisdiction limiting/date localization/marker stripping AFTER the model responds, so streaming the model's raw tokens would risk showing not-yet-safety-checked text on screen. Once the final text exists server-side, it is written as `text/event-stream` in `_STREAM_CHUNK`-sized (24 chars) `event: chunk` pieces `_STREAM_DELAY` apart (20ms), then one `event: done` carrying the exact JSON body `/api/chat` would have sent (so the widget can still render `opciones`/`turnos`/`whatsapp`/`login`/`titulo`/`fuentes`). The ASGI topology owns this with a real native `StreamingResponse`; the dark stdlib topology retains `_message_stream` and connection-close framing as rollback. Neither path declares `Content-Length`, and the native response never copies backend-only hop-by-hop headers. `static/platform/chat-widget.mjs`'s `enviarMensaje` parses the SSE framing off `fetch(...).body.getReader()` (EventSource cannot POST a body) and calls `lista.updateBubble(el, role, texto, opts2)` to re-render the SAME bubble node as chunks arrive, finishing with a markdown-and-links final pass on `done`. Error paths (429/400) never open the stream — they get a normal one-shot JSON response, same status codes as `/api/chat`.

- **Shared chat component + quick-reply options + header entry point (2026-08-01).** Four related changes, all touching this surface:

- **One conversation per patient across web and WhatsApp; session rollover; memory across sessions (2026-08-03).** Three connected changes on top of the 2026-08-02 handoff work above — EXTENDS that design (same linking criterion, same `chat_messages`/`chat_handoffs` tables), no parallel mechanism.
  - **Storage is unchanged**: still one row per (`channel`, `key`) in `chat_messages`, written exactly as before (`db_chat.chat_save_message`) — `test_canales_no_se_mezclan` still holds. What's new is entirely READ-side: `chat_agent._conversation_pairs(usuario, canal, clave)` widens the set of (channel, key) pairs a turn's context is loaded from, whenever `usuario` is an AUTHENTICATED identity (never guessed from the request body — the caller already resolved it: `chat_api.py`'s session cookie, or `whatsapp_chat.py`'s phone match). Two new db functions do the linking lookup: `db_chat.linked_whatsapp_claves(dni, contact, grant_days)` returns `"tel:<digits>"` keys either (a) matching the account's own registered `contact` (same last-10-digits normalisation as `user_by_phone`) or (b) a phone that redeemed a handoff code minted by THIS dni's logged-in session, still within `TURNOS_WA_HANDOFF_GRANT_DAYS` (reverse of `user_by_handoff_phone`); `db_chat.web_claves_for_dni(dni, limit=3)` returns the most recently active web `"dni:<dni>"`/`"dni:<dni>:chat:<session>"` keys (the widget mints a fresh `session_id` per browser tab, so "the" web conversation for a WhatsApp turn is really "whichever tabs were recently active", capped small). **Privacy invariant**: a phone that never linked (no matching `contact`, no redeemed handoff code from this dni) never appears in either lookup — an anonymous/unrelated WhatsApp number can never read into someone else's account conversation, and an anonymous web visitor (`usuario=None`) never triggers any merge at all. New db function `db_chat.chat_history_multi(pares, limit)` fetches the merged, chronologically-sorted timeline across all the pairs in one query.
  - **Session rollover (`TURNOS_CHAT_SESSION_GAP_HOURS`, default 24, hard-capped [1, 336]).** `chat_agent._split_session(filas, gap_hours, ahora=None)` finds the most recent gap of `gap_hours` or more in the merged timeline — INCLUDING the gap between the last stored message and right now (context is loaded BEFORE the incoming message is saved, so a lone message from days ago must roll over on the very next turn, not wait for a second stored message to detect the gap against). Everything before that boundary is `cerrados` (the just-closed session); everything after is `actuales`, and ONLY `actuales` is handed to the model — the stale transcript is never replayed verbatim. This also makes the existing "first message of a new chat" `[titulo: …]` instruction (chat_agent.py, 2026-07-23) fire again for free: it's gated on `historial` having no `user` turns, and a rollover simply makes `historial` empty. Applies uniformly to both surfaces at the read layer — independent of, and does not replace, `static/platform/chat-widget.mjs`'s own 4-hour client-side `separarTrasPausa()` (which mints a brand-new `session_id`/conversation tab on the web side only); the server-side cut is what actually matters for WhatsApp, which has no client of ours to run that JS.
  - **Memory across sessions (RAG-lite, no embeddings).** New table `chat_summaries(id, patient_key, channel, summary, message_count, covers_until, created)` — `patient_key` is always `"dni:<dni>"`; **anonymous sessions are never summarized** (no stable identity to hang memory off of, `chat_agent._patient_key` returns `""` and every summarization/injection function no-ops on that). When `_split_session` finds a `cerrados` session, `chat_agent._maybe_summarize_closed_session` checks `db_chat.chat_summaries_latest_covers(patient_key)` (the most recent `covers_until` already stored) — if it's `>=` the closed session's own last-message timestamp, it's already been summarized and this is a no-op (idempotency: the first turn of a new session triggers the summary, every later turn of that same session sees the boundary already covered and skips). Otherwise `chat_agent._resumir_sesion` calls the SAME AI client as the rest of the chat (`ai_client.py`, `TURNOS_AI_MODEL`) with a small single-shot prompt (2-4 sentences, Spanish, third person, "never invent facts absent from the transcript") and the result is capped and stored via `db_chat.chat_summary_save`. **`TURNOS_FAKE_AI=1` still works**: `_resumir_sesion` returns a deterministic stand-in (`"(resumen fake) <first user line>"`) with no network call, same convention as `chat_agent._fake_step`. **A summarization failure (no key, network, bad JSON) is a silent skip** — caught, logged, no row written, the chat's own reply is entirely unaffected (spec: "nothing breaks because of AI"). On the next new session, `chat_agent._memory_block(usuario)` reads the most recent `TURNOS_CHAT_SUMMARY_COUNT` summaries (default 3, capped [1,10]) via `db_chat.chat_summaries_recent` and injects them into the system prompt as a clearly delimited, size-capped block (`MAX_MEMORY_BLOCK_CHARS`, header/footer marking it as background memory the model must never quote verbatim) — recency-based retrieval, deliberately no embeddings/pgvector at this scale.
  - **Widget hydration**: `chat_agent.thread_for_widget(usuario, canal, clave)` returns the current session's turns (post rollover-cut, cross-surface merged) as plain `{"rol","texto","canal"}` — markers stripped, tool turns skipped. New route `GET /api/chat/history?session_id=…` (`chat_api.py`) is the widget's entry point: identity ALWAYS from the session cookie (never the query string), so an anonymous/expired session gets `{"mensajes":[]}` immediately, never an error and never someone else's history. A FRESH conversation paints its predefined localized greeting synchronously before `static/platform/chat-widget.mjs` calls `sincronizarHistorial()`, so network latency can never place the greeting after the user's first response. If remote turns come back while the conversation is still untouched, they are appended through the existing `addMsg`/`lista.addBubble` pipeline; once the person has written, a late history response is ignored. The per-conversation `hidratado` flag (sessionStorage) keeps the fetch idempotent. (`static/platform/chat-widget.mjs` is content-hash fingerprinted — every reference resolves through `static_fingerprint`, nothing to bump.)

## Autocompaction of a long session (2026-08-03)

The gap cut (`_split_session`) only closes a session after hours of silence. A
conversation that keeps going the same day was never cut, and `_load_history`
trimmed it by silently dropping the OLDEST messages — so past a certain length
the assistant forgot the first thing the person said, which is usually the
reason for the consultation.

Now, when the open session goes past its budget, the head is summarised and the
context becomes `[system: summary of the earlier part] + [verbatim tail]`. Same
idea as the session cut, but inside the session and without losing the thread.

- **Budget:** `COMPACT_TRIGGER_CHARS` = 40k chars (~10k tokens), deliberately
  large — compacting is the exception, not the normal case. Override without a
  deploy via `TURNOS_CHAT_COMPACT_CHARS`.
- **Verbatim tail:** the last `COMPACT_KEEP_TAIL_TURNS` (12) messages.
- **Cost control:** once compacted, it is only redone after
  `COMPACT_REDO_CHARS` (12k) of new material accumulates outside the tail — not
  once per turn.
- **Storage:** `chat_compactions`, one row per patient, superseded in place
  (compaction N+1 is written from compaction N plus what followed, so the row
  always describes "everything up to `covers_until`").
- **Not `chat_summaries`.** That table holds CLOSED sessions and every row of it
  is injected into the NEXT session's system prompt. A compaction is the head of
  a session that is still open and must never become cross-session memory —
  closing a session therefore deletes its compaction (`chat_compaction_clear`).
- **Anonymous chats are not compacted:** no stable identity to store the summary
  against, and recomputing per turn would cost one model call per message. Those
  keep the old trimming (they are short — there is a per-day message cap).
- Privacy: the compaction call goes through `pii.py` like every other outbound
  call, and the summary is stored restored (real names), never tokenised — see
  [legal.md](legal.md).


## Human decisions and disclosure (2026-10-14)

The shared cancellation tool now returns the patient's `/request/<id>` page;
it never executes a model-selected cancellation. For automatically confirmed
services/same-day openings, the request tool returns the service booking page
for a human submit. Other assistant requests are pending, with the trusted
`allow_auto_confirmation=False` domain argument so a concurrent catalog change
cannot grant approval. Model-supplied arguments cannot override this flag.
Undeclared tool callables cannot execute in the engine, and approval/rejection/
reassignment/clinical-write tools remain human-only. The web widget discloses AI
before its composer. Every first WhatsApp reply, including handoff/auth/media
paths, starts with the same notice; a persisted technical disclosure marker
prevents repeated notices. No new outbound notification channel was added.

A request or cancellation is told as done only from the domain's receipt (the
`confirmation_required` proposal, `confirm_booking_reply`). When a turn tried
`request_appointment`/`cancel_request` and every attempt was refused, a final
model line that claims success («Listo, tu turno quedó confirmado», the same in
the ten languages: `_DONE_CLAIM_RE`) is replaced by what happened —
`assistant.action_needs_login` (+ login button) for an anonymous visitor,
`assistant.action_not_done` otherwise. An honest explanation of the refusal
passes untouched; a read (`my_requests`) is not an action (QA P09,
`tests/test_chat_action_receipt.py`).

An unknown coverage stays unknown. The prompt says it (never map an unfamiliar
coverage name onto a known program, never promise coverage or authorization,
never ask for card photos or documents in the chat), and the code enforces it:
when the patient's message asks about a coverage (`_COVERAGE_Q_RE`), every reply
sentence that says what a plan covers, guarantees or used to be called
(`_COVERAGE_CLAIM_RE`) is dropped unless it names one of the turn's RAG
references, and the reply then leads with `assistant.coverage_unknown` (QA P05:
«la CUS, antes llamada Cobertura Sintética, garantiza… Dermatología»;
`tests/test_chat_coverage.py`).

An explicit «sólo los pasos» (`_STEPS_ONLY_RE`, ten languages) is a how-to
question, not a slot request: it forces no lookup and its reply carries no slot
cards or `?slot=` links. «No reserves» alone is not enough — «fijate si hay
pediatría mañana, no reserves» still wants availability (QA P01).

The conversation language is the first message's, until the patient explicitly
asks for another one (`chat_language.requested`: «Ahora en español», «reply in
English», «Answer in Russian»). That request moves the prompt rule AND the
application's own lines (`idioma_turno`: link labels, canned replies) and holds
until the next explicit request; writing in another language or mentioning one
(«¿el médico habla inglés?») moves nothing (QA P04). After logging in a person
manages their own appointments and those of the people in their care — the
prompt says so and forbids «todo» (QA P12). Proofs:
`tests/test_chat_qa_followups.py`.


Voice dictation uses the separate Fal upload/queue transport in voice.py. Its
runtime model lives in the existing chat_voice overlay, resolved by the shared
core/ai_policy.py. The register lists it separately. TURNOS_AI_DISABLED=1 and
TURNOS_VOICE_ENABLED=0 stop upload and queue calls; fake mode returns a synthetic
transcript and does not offer real microphone capture. The shared composer
shows ai.notice.voice on the first press of the available microphone, which
does not record (the next press does; sending puts the notice away), so the
notice never takes the answer field of someone who types. Raw audio
is a documented transcription exception; post-transcription chat text is filtered.


## When the assistant is down: emergency first, honest outage otherwise (2026-10-25)

QA (codex-pinamar-chat-qa-20261025) found that «Tengo dolor de pecho y
dificultad para respirar ahora» got «el asistente no está disponible… sacar
turnos» whenever the model was down. Every degraded reply is written by the
code, so the code decides, without a model:

- **Urgent conversation → the emergency action leads.** `chat_agent._is_urgent`
  is the red-flag list (`_EMERGENCY_RE`) plus a declared emergency
  (`_DECLARED_EMERGENCY_RE`: «es una emergencia», «urgente», «ambulancia», the
  same in the ten shipped languages; plural «urgencias» is the department's
  name and stays out). `_urgent_conversation` also looks at the session's
  earlier user messages, so «¿Me quedo esperando acá?» after «Es una
  emergencia» still escalates (QA P17). The line (`assistant.emergency`) goes
  first on every degraded path: no key, breaker open, daily limit, timeout,
  empty or blank answer, too many steps, the off-topic scope reply, and the
  transport's own 429 (`chat_api`, which answers in the language the patient
  wrote in and sees only the current message — it never reads the history). A
  healthy model still writes its own answer. The look-back covers the
  session's retained history only (`_load_history`: the last turns within the
  character budget; a failed history read is an empty one).
- **The number is the installation's.** `site_identity.get("emergency_number",
  "")` — the pack's `sitio.json` or the Settings override, the same value the
  footer's «Urgencias» links. The code default (`_DEFAULTS`) is deliberately
  NOT used: without a configured number the line says «llamá a emergencias»
  (`assistant.emergency_no_number`).
- **Anything else → an honest outage.** `assistant.unavailable` is a
  remedy, not an error line (2026-10-28, `remedies.py` spirit): «Por ahora no
  podemos responderte por chat. Mirá los horarios y sacá tu turno en
  {services}; …» — never «I could not check anything», which is false when a
  tool already returned before the model failed — and names two app-owned
  links («Servicios y turnos» → `/`, «Centros de salud» → `/centers`). When the
  patient named a service (this message or an earlier one), its published
  `horario` comes straight from the catalog (`chat_tools.published_hours`) under
  «Horarios publicados en la web:», with the service page linked (QA P18). No
  WhatsApp, no «te respondemos más tarde», no person: nobody would write that
  answer. A timeout now gets this same reply instead of «probá de nuevo en un
  rato» (`assistant.error` is gone). The empty-answer «¿Podés repetirlo?» stays
  for a non-urgent message.

Proofs: `tests/test_chat_degraded.py` (five conditions × ten languages, P17,
P18, recovery, the 429).
